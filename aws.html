AWS — architektura i wybór usług

Compute, ingress, messaging, networking, security, storage i operacje produkcyjne

1. Decyzje compute: granice izolacji i kosztu

Lambda uruchamia kod na żądanie, izolując standardowe środowiska wykonawcze; ECS/Fargate utrzymuje procesy i samodzielnie kontroluje ich lifecycle. EC2 przenosi na zespół zarządzanie OS, patchingiem i pojemnością hostów. Wybór zależy od rozkładu ruchu, czasu pracy, latency SLO, statefulness i zależności. Nie porównuj wyłącznie ceny vCPU: dolicz load balancer, NAT, logi, provisioning, idle capacity i pracę operacyjną. Przy stałym ruchu zmierz koszt jednostkowy przy docelowym p99; przy burstach sprawdź ramp-up i ograniczenia downstream. Lambda · ECS/Fargate/EC2.

2. Izolacja ruchu i blast radius

Osobne konta produkcji i dev, role cross-account z ograniczoną trust policy, budżety i regionalne service quotas. Rozdziel workload publiczny, workerów i batch przez osobne kolejki, role, funkcje i pule DB. Jedna wspólna regionalna quota może zablokować niezależne usługi. AZ chroni przed awarią lokalną, nie przed błędnym wdrożeniem ani utratą Regionu; multi-region wymaga strategii danych, routingu, RPO/RTO i testowanego failover. IAM i VPC.

3. Łańcuch ograniczeń i wybór integracji

Przykład: API Gateway przyjmuje zlecenie, Lambda waliduje i zapisuje outbox, SQS przejmuje skoki ruchu, worker ogranicza obciążenie RDS/SAP. Limit 5000 RPS na wejściu nie oznacza 5000 zakończonych zadań/s. Projektuj od najwolniejszego komponentu; każde ogniwo ma niezależne timeouty, retry i quotas. Dla uploadu użyj presigned URL i S3, dla fan-out SNS, dla routingu zdarzeń EventBridge, dla workflow z trwałym stanem Step Functions. API Gateway · Messaging · S3.

4. Infrastructure as Code i deploy

CDK syntetyzuje CloudFormation, Terraform przechowuje stan i planuje diff. Przeglądaj replacement zasobów, drift i zależności. Stan Terraform może zawierać sekrety; ogranicz dostęp, szyfruj, blokuj równoległy apply. Pipeline buduje niezmienny artefakt (digest), skanuje, promuje tę samą wersję i wykonuje canary/rolling z metrykami. Rollback kodu nie cofa migracji danych: expand/contract i kompatybilność eventów pozwalają współistnieć starym i nowym wersjom. Deletion protection, backup i restore test ograniczają skutki błędu IaC.

5. Observability, koszt i niezawodność

Zdefiniuj SLI biznesowe (np. zamówienie potwierdzone w 60 s), nie tylko status 200. Metryki RED: rate, errors, duration; USE: utilization, saturation, errors. CloudWatch alarms na p99, age kolejki, throttles i DB wait; logi JSON z correlation ID; trace propagowany przez HTTP i message attributes. Kontroluj cardinality metryk (nie wymiar orderId), retencję i sampling. RPO oznacza tolerowaną utratę danych, RTO czas odzyskania; snapshot bez restore drill nie potwierdza żadnego z nich. AWS Budgets nie jest natychmiastowym hard cap. Taguj koszty, mierz NAT/data transfer, requests i storage transitions.

Praktyka: capacity i koszt

5000 RPS i średni czas 150 ms oznacza średnio 750 concurrent invocations. Przy 1 GiB RAM i 100 mln wywołań po 150 ms zużycie to 15 mln GB-s, przed dodatkowymi kosztami, free tier i init. Dla ECS zmierz throughput taska przy docelowym p99, uwzględnij rolling overlap, idle capacity oraz dodatkowe koszty LB/NAT. Porównuj dobowy workload, a nie tylko peak.

Failover Regionu wymaga promocji writer DB, kontroli RPO, routingu i ochrony przed split brain. DNS TTL i cache klientów mogą utrzymywać stary endpoint. Nie deklaruj multi-region HA bez testu failover i procedury powrotu.
