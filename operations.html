SLI/SLO, tracing, metryki, capacity i konkretne runbooki

1. SLI i error budget

SLI jest mierzalnym zachowaniem użytkownika, SLO celem (np. 99.9% poprawnych API responses poniżej 300 ms w 30 dni). Dla async mierz od durable acceptance do terminal result; HTTP 202 nie jest dowodem realizacji. Error budget = 1-SLO; przy 1 mln kwalifikowanych operacji i 99.9% SLO budżet to 1000 nieudanych. Burn rate = observed bad fraction / allowed bad fraction, np. 1% przy 0.1% budget to 10×. Wielooknowe alerty (krótkie + długie okno) ograniczają szum i wykrywają szybkie spalanie. Nie wykluczaj 429 bez uzasadnienia biznesowego: overload widoczny przez użytkownika może być naruszeniem SLO. RPO/RTO oddziel od availability, testuj odzyskanie.

2. Logs, metrics, traces i cardinality

Structured JSON z timestamp, service, version, severity, traceId, requestId i eventId; nie loguj danych osobowych/sekretów. Metrics counters/rates, gauges i histograms; p95 per replica nie daje globalnego p95 przez uśrednienie, agreguj buckets lub odpowiedni histogram. Unikaj userId/orderId jako labels, bo cardinality powoduje koszt i problemy query; użyj logów/traces/exemplars. Traces: span per operacja, W3C traceparent propagate w HTTP i event metadata, async fan-out może korzystać ze span links. Sampling head ogranicza koszt, tail może zachować błędy/slow traces, wymaga buforowania. Nie uznawaj braku trace za brak requestu. Collector pipeline batch/export ma limity pamięci i retry; telemetry outage nie powinien blokować biznesowej ścieżki. CloudWatch/X-Ray lub OpenTelemetry + backend, korelacja dashboardów z deployment version.

3. Runbook: p99 rośnie, CPU aplikacji niskie

Sprawdź rate i error mix oraz czy wzrost dotyczy jednej trasy/tenant/AZ/deploy. Rozbij trace na queue wait, DNS/TCP/TLS, DB acquisition, query execution i downstream. Niski CPU może oznaczać lock, socket/connection saturation, threadpool, I/O. Pool waiting rośnie + DB active sessions high: ogranicz concurrency, sprawdź pg_stat_activity/wait events i blocker; nie zwiększaj poola w ciemno. Event-loop delay high przy CPU niskim w całym klastrze: sprawdź per-core/process oraz GC, CPU throttling, synchronizację. Jeśli nowy release: rollback/feature flag gdy bezpieczne względem migracji; zbierz evidence przed zmianą. Po mitigacji potwierdź p99 i SLO, zapisz root cause i test regresji.

4. Runbook: rośnie backlog i DLQ

Porównaj enqueue rate, completed throughput, age i in-flight. Jeśli worker CPU/sessions wolne, sprawdź concurrency cap, poll errors, FIFO hot group, visibility timeout i retry. Jeśli DB/SAP saturated, zmniejsz consumer concurrency i ogranicz ingest zamiast skalować. Jeśli DLQ rośnie po deploy, zatrzymaj redrive, sprawdź schema mismatch lub permanent errors; odtwórz pojedynczy event na izolowanym środowisku. Dla timeout po side effect najpierw reconcile. Po fix redrive małymi partiami z cap, monitoruj duplicates i age; nie kasuj DLQ bez audytu. Zdefiniuj queue drain estimate: backlog/(service rate-arrival rate) tylko gdy service rate większy od arrival rate.

5. Runbook: AWS throttling / deploy

API Gateway 429 + Lambda Throttles: rozdziel account/route throttle od reserved concurrency, sprawdź duration i concurrency regionalną innych funkcji. 502/504: integration error/timeout i wynik biznesowy, nie zakładaj rollback. ECS pending: subnet IP, capacity provider, quota i task definition; stoppedReason, OOM, ECR/Secrets endpoint i SG. DB failover: reconnect, ogranicz retry storm, nie powtarzaj nieznanego COMMIT bez idempotency. W przypadku naruszenia bezpieczeństwa izoluj zasób/role, zachowaj logi i koordynuj rotację; nie usuwaj śladów audytowych. Incident commander, timeline, komunikacja, owner następnych kroków. Postmortem: contributing factors, detection/mitigation/recovery, konkretne działania i weryfikowalny termin.

6. Production readiness i delivery

Przed wdrożeniem: owner, SLA zależności, SLO, capacity i quotas, IAM least privilege, secrets rotation, backup restore, graceful shutdown, retry/idempotency, schema compatibility, alarms i runbooks. Deployment canary/blue-green nie chroni gdy obie wersje współdzielą destrukcyjnie zmieniony schemat; expand/contract i feature flags. Release artifact immutable, rollback tested, config versioned. Feature flags z owner/expiry, nie stała złożoność. Chaos/game day sprawdza np. utratę AZ lub dependency timeout z bezpiecznym zakresem. Cost anomaly i service quota utilization mogą być leading indicators; nie traktuj kosztów jako wyłącznie problemu finansowego.
