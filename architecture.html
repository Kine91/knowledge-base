Mikroserwisy — system design i niezawodność

Granice domen, consistency, capacity, odporność, observability i ewolucja

1. Bounded contexts i data ownership2. Consistency, CAP, invariants3. Saga, orchestration, choreography4. HTTP/gRPC, kontrakty i budgets5. Capacity planning i backpressure6. Cache i read models7. API evolution, rollout, observability8. Bezpieczeństwo i multi-tenancy

1. Bounded contexts i data ownership

Granica serwisu powinna odpowiadać niezależnej zdolności biznesowej, invariantom i odpowiedzialności zespołu. Rozdziel Orders, Inventory i Billing tylko gdy mają odmienne lifecycle i ownership. Database per service oznacza brak bezpośrednich zapisów i zależności na cudzym schemacie; osobne schematy w jednym klastrze mogą być kompromisem przejściowym, nie niezależnym failure domain. Jeśli większość zmian wymaga skoordynowanych deploymentów i transakcji przez sieć, masz distributed monolith. Modular monolith z egzekwowanymi granicami jest lepszy, gdy zespół mały, domena niestabilna i nie ma niezależnych wymagań skalowania. Strangler fig migruje funkcję po funkcji, z kontrolą routingu i ownership danych; nie rób niekoordynowanego dual write do starego i nowego systemu.

2. Consistency, CAP, invariants

CAP dotyczy wyboru podczas partycji sieciowej: system nie może zapewnić równocześnie linearizable consistency i dostępności rozumianej jako odpowiedź każdego nieuszkodzonego węzła. To nie jest wybór dowolnych dwóch cech w każdych warunkach. PACELC przypomina o kompromisie latency/consistency poza partycją. Eventual consistency oznacza zbieżność bez dalszych zmian, nie określony czas. Zdefiniuj które invariants wymagają jednego właściciela i atomowej operacji (saldo, dostępność towaru), a które widoki mogą być opóźnione. Read-your-writes dla UI: writer read, version token lub status operacji. W przypadku opóźnionych eventów użyj aggregate version, nie timestamp jako jedynego źródła kolejności.

3. Saga, orchestration, choreography

Saga: lokalne transakcje i kompensacje. Order PENDING → reserve stock → authorize payment → CONFIRMED. Payment timeout nie oznacza odrzucenia; najpierw sprawdź wynik z idempotency key. Kompensacja nie cofa czasu: zwrot środków to nowa operacja i może się nie udać. Wprowadź statusy COMPENSATING, MANUAL_REVIEW i deadline; retry kompensacji oraz audyt. Choreography (eventy) upraszcza małe workflow, ale ukrywa globalny przebieg i tworzy cykle; orchestration (np. Step Functions) jawnie utrzymuje stan i odpowiedzialność, ale koordynator nie powinien posiadać cudzych reguł domenowych. Saga nie zapewnia izolacji ACID; rezerwacje z TTL i wersjonowaniem muszą zapobiegać konfliktom. Outbox/inbox usuwa dual write, nie rozwiązuje automatycznie rozproszonej atomowości.

4. HTTP/gRPC, kontrakty i budgets

HTTP/JSON ułatwia integracje publiczne, gRPC daje typowany kontrakt Protobuf, streaming i multiplexing HTTP/2, ale wymaga odpowiedniej infrastruktury i obsługi browser (gRPC-Web/proxy). Propaguj deadline i cancellation, nie tylko timeout per hop. Jeśli budżet klienta 1 s, usługa A zużywa 150 ms, nie przekazuj B domyślnych 5 s; zostaw budżet na odpowiedź. Fan-out równoległy może skrócić średnią, ale p99 zależy od najwolniejszej gałęzi. Retry tylko operacje bezpieczne/idempotentne, z limitem prób i deadline; trzy warstwy po trzy próby mogą stworzyć 27 wywołań. Circuit breaker open odcina chory downstream, half-open próbuje ograniczoną liczbę wywołań; bulkhead wydziela osobne pule i kolejki per dependency/tenant. Nie ukrywaj trwałych błędów fallbackiem dającym błędne dane.

5. Capacity planning i backpressure

Little's Law L=λW: 5000 RPS × 20 ms zajęcia połączenia = średnio 100 połączeń, nie 5000. Dla 5000 RPS × 200 ms = 1000; DB ma 500 połączeń, a realny limit może być niższy przez CPU/locks/I/O. Zmierz throughput w load test z realnym mixem i rozkładem latency. Ustaw globalny budżet (np. 350 DB sessions dla API, 100 workers, 50 reserve), per-instance pool z uwzględnieniem max replicas i rolling overlap. Bounded queue na synchronicznej ścieżce, timeout acquisition, 429 dla limitu klienta, 503 dla przeciążenia usługi. Dla async 202 po potwierdzonym trwałym przyjęciu, status resource, retention/retry/DLQ. Jeśli arrival rate stale przewyższa service rate, kolejka tylko odkłada awarię; ogranicz ingest albo zwiększ bezpieczny throughput. DB performance · Queue capacity.

6. Cache i read models

Cache-aside: miss → DB → cache, write → DB commit → invalidate; race między miss reader i writer może ponownie wstawić stary rekord. TTL ogranicza staleness, wersja rekordu/conditional cache update albo event invalidation zmniejsza okno. Cache stampede: per-key singleflight, jitter TTL, stale-while-revalidate dla danych tolerujących staleness; distributed lock wymaga lease i fencing dla correctness. Cache penetration: negative cache z krótkim TTL. Redis eviction i awaria nie mogą naruszać invariantów. CQRS rozdziela model zapisu i odczytu, nie wymaga event sourcing. Event sourcing przechowuje fakty, wymaga replay, snapshotów, versioningu i obsługi zmian semantyki; nie wybieraj go wyłącznie dla audytu.

7. API evolution, rollout, observability

OpenAPI i schema registry pozwalają testować kompatybilność; dodanie required field, nowa wartość enum lub zmiana semantyki może zepsuć konsumenta. Expand → deploy tolerant readers → producer → migrate → contract. SLO np. 99.9% poprawnych operacji w 30 dni, error budget 0.1%; p95 nie zastępuje odsetka requestów spełniających deadline. Trace context (W3C traceparent) propaguj w eventach, loguj eventId/orderId jako pola logów, nie labels metryk. Alertuj na burn rate i age backlogu, nie samą liczbę wyjątków. Incident: najpierw ogranicz blast radius (feature flag, throttle, pause consumer), zbadaj timeline i korelacje, przywróć, potem bezwinny postmortem z action items.

8. Bezpieczeństwo i multi-tenancy

Authentication ≠ authorization: JWT podpis, issuer, audience, exp; resource-level access każdorazowo w serwisie. RBAC dla ról, ABAC dla tenant/ownership i kontekstu; tenantId z zaufanej tożsamości, nie body. BOLA/IDOR: endpoint /orders/:id musi filtrować po tenantId również w zapytaniu. Serwis-serwis przez role/mTLS/token z właściwym audience; nie forwarduj bez potrzeby tokenu użytkownika. SQL injection przez parametryzację wartości i allowlist identyfikatorów; SSRF przez allowlist destinations, DNS/IP validation i egress policy. Threat model na granicach trust, rate limits, audit log z ograniczoną ekspozycją PII. AWS IAM/VPC.
