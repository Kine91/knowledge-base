Mikroserwisy i system design

Granice usług, spójność, komunikacja, odporność

Zagadnienie 1 / 5

Granice serwisów

Dziel według bounded context i własności danych, nie według tabel ani warstw. Serwis Orders jest właścicielem zamówień; Inventory właścicielem stanów. Unikaj wspólnej bazy z zapisem z wielu usług.

Praktyka / decyzja projektowa

Projekt: Order API tworzy zamówienie w statusie PENDING, rezerwacja zapasu odbywa się osobną operacją. Zdefiniuj kontrakt i właściciela każdego pola.

Pytanie senior / pułapka

Pytanie: kiedy monolit modułowy jest lepszy? Odpowiedź: gdy brak niezależnych wymagań skalowania, stabilnych granic lub dojrzałości operacyjnej.

Zagadnienie 2 / 5

Synchronicznie czy asynchronicznie?

HTTP/gRPC gdy odpowiedź jest potrzebna natychmiast; kolejka/event przy rozluźnionym sprzężeniu i tolerancji opóźnienia. Synchroniczny łańcuch N usług zwiększa latency i ryzyko propagacji awarii.

Praktyka / decyzja projektowa

Dla checkout trzymaj krótki synchroniczny krytyczny odcinek; fulfillment i powiadomienia emituj asynchronicznie. Propaguj correlation ID.

Pytanie senior / pułapka

Nie myl eventu faktu (OrderPlaced) z komendą (ReserveStock); określ kto odpowiada za rezultat.

Zagadnienie 3 / 5

Spójność i saga

Transakcja ACID nie rozciąga się automatycznie na kilka baz. Saga koordynuje lokalne transakcje i kompensacje; nie zapewnia pełnej izolacji.

Praktyka / decyzja projektowa

Przebieg: create order → reserve stock → authorize payment; przy błędzie płatności release stock i cancel order. Uwzględnij nieudane kompensacje.

Pytanie senior / pułapka

Pytanie: co gdy event jest dostarczony dwukrotnie? Handler musi być idempotentny.

Zagadnienie 4 / 5

Odporność i backpressure

Timeout, ograniczona współbieżność, rate limit, circuit breaker i retry z jitterem muszą być zaprojektowane wspólnie. Retry bez limitów wzmacnia awarię.

Praktyka / decyzja projektowa

5000 req/s i 500 połączeń DB: zmierz czas zajęcia connection, limity pool per pod i RPS. Kolejkuj tylko prace asynchroniczne; synchroniczne przeciążenie zwróć 429/503.

Pytanie senior / pułapka

Nie obiecuj «zero utraty» przy niedostępności infrastruktury bez zdefiniowanych gwarancji przyjęcia, durabilty i recovery.

Zagadnienie 5 / 5

Observability i ewolucja kontraktów

Śledź p95/p99 latency, error rate, saturation, queue age, consumer lag; logi strukturalne, trace IDs i alerty na SLO.

Praktyka / decyzja projektowa

Wersjonuj kontrakty kompatybilnie: add optional field → deploy consumers → deploy producer → migrate → remove old field.

Pytanie senior / pułapka

Unikaj breaking changes i kaskadowych deploymentów.
