AWS IAM, VPC, RDS — granice dostępu

Polityki, sieć, credentials, failover i troubleshooting

1. IAM evaluation i STS2. VPC routing i security groups3. Debugowanie łączności4. Secrets i encryption5. RDS i Aurora — HA nie oznacza skalowania zapisów

1. IAM evaluation i STS

Trust policy decyduje kto może AssumeRole, identity policy jakie akcje wykonuje rola. STS wydaje krótkotrwałe credentials; SDK odświeża je z provider chain. Explicit deny wygrywa, SCP i permission boundary zwykle ograniczają maksymalne uprawnienia, nie nadają ich. Resource-based policy może dać dostęp bez identity allow w niektórych przypadkach same-account; szczegóły zależą od principal ARN (role vs role session), cross-account zwykle potrzebuje obu stron. KMS key policy ma własną semantykę. Ogranicz iam:PassRole do konkretnych ról/usług: możliwość przekazania szerokiej roli do compute jest ryzykiem privilege escalation. Dla GitHub Actions OIDC zamiast stałych kluczy, warunki aud/sub do repo i branch/environment.

2. VPC routing i security groups

Public subnet ma trasę do Internet Gateway, ale zasób potrzebuje public IP i reguł. Private subnet korzysta z NAT dla outbound IPv4 albo endpoints. Security group jest stateful (odpowiedzi do dozwolonego połączenia automatyczne), NACL stateless (uwzględnij ephemeral ports). Preferuj SG references: ALB→app SG→RDS SG na konkretnym porcie. NAT per AZ zmniejsza zależność od jednej AZ i cross-AZ transfer; VPC endpoints dla S3/DynamoDB gateway, dla wielu usług interface z private DNS i opłatą per AZ/traffic. VPC endpoint policy nie zastępuje IAM. CIDR planuj na burst ECS/ENI oraz peering bez overlap.

3. Debugowanie łączności

DNS resolution → route → SG/NACL → TCP connect → TLS → auth. Timeout zwykle wskazuje brak ścieżki lub blokadę, connection refused aktywne odrzucenie, certificate error problem z TLS/hostname, 403 autoryzację (nie zawsze IAM). VPC Flow Logs pokazują ACCEPT/REJECT metadanych, nie treści; Reachability Analyzer analizuje konfigurację, nie zdrowie procesu. Route 53 private hosted zone może zasłaniać publiczny rekord; peering jest nietranzytywny. Przy SAP on-prem ustal VPN/DX, redundancję, DNS, certyfikaty, firewall i ownership obu końców.

4. Secrets i encryption

Secrets Manager rotation wymaga, by konsumenci odświeżali cached credentials i odzyskiwali połączenia; environment variables w ECS nie aktualizują się same po zmianie secretu (nowy task lub runtime fetch). Parameter Store/Secrets Manager dobieraj do kosztu, rotacji i potrzeb; nigdy nie loguj sekretów. Envelope encryption: KMS chroni data key, dane szyfruje lokalny klucz; nie używaj KMS Encrypt jako storage dużych payloadów. CloudTrail rejestruje API actions, data events mogą wymagać włączenia. Oddziel role runtime/deploy/admin, ogranicz break-glass i audytuj.

5. RDS i Aurora — HA nie oznacza skalowania zapisów

Multi-AZ RDS DB instance ma standby do failover, nie read scaling; Multi-AZ DB cluster ma inne możliwości. Read replicas są asynchroniczne, mogą zwracać stary stan po zapisie; krytyczny read-your-writes kieruj do writer lub użyj jawnego mechanizmu wersji. Aurora oddziela storage od compute, ale writer ma nadal ograniczoną przepustowość. Failover zmienia dostępny endpoint/połączenia, aplikacja musi reconnectować z backoff; transakcja z utraconym wynikiem może być zatwierdzona. RDS Proxy ogranicza connection churn i pomaga przy failover, nie eliminuje pinning ani lock contention. Backup/PITR i restore do nowej instancji testuj; monitoruj replication lag, DB connections, CPU, IOPS/latency i wait events. SQL i transakcje.
