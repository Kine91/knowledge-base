SQS, SNS i niezawodność zdarzeń

Durability, retry, DLQ, outbox, idempotencja

1. SNS vs SQS2. Standard vs FIFO3. Visibility timeout i DLQ4. Transactional outbox5. Skalowanie workerów
Zagadnienie 1 / 5

SNS vs SQS

SNS publikuje do subskrybentów (fan-out); SQS buforuje prace dla konsumentów. Typowy wzorzec: SNS topic → osobne kolejki SQS dla billing i analytics.

Praktyka / decyzja projektowa

Każdy consumer ma własny retry, DLQ i skalowanie. Polityką filtra SNS ograniczaj niepotrzebne zdarzenia.

Pytanie senior / pułapka

SNS sam w sobie nie jest trwałą kolejką roboczą dla offline consumerów.

Zagadnienie 2 / 5

Standard vs FIFO

SQS Standard: at-least-once, best-effort ordering; FIFO: porządkowanie w obrębie MessageGroupId i deduplikacja w określonym oknie, lecz nie «exactly once» end-to-end.

Praktyka / decyzja projektowa

Dla zamówień MessageGroupId = orderId; nie używaj jednej grupy globalnie, bo ogranicza równoległość.

Pytanie senior / pułapka

Obsłuż duplikaty po stronie DB unikalnym idempotency key.

Zagadnienie 3 / 5

Visibility timeout i DLQ

Po pobraniu wiadomość staje się tymczasowo niewidoczna, a nie usunięta. Usuń dopiero po sukcesie. Dopasuj visibility timeout do wykonania; rozważ heartbeat/change visibility.

Praktyka / decyzja projektowa

Błąd przejściowy → retry z opóźnieniem; błąd trwały → DLQ i alert. Monitoruj oldest message age oraz liczbę receive attempts.

Pytanie senior / pułapka

Nie usuwaj wiadomości przed commitem DB; nie retryuj bez końca błędów walidacji.

Zagadnienie 4 / 5

Transactional outbox

Problem dual write: commit DB i publikacja do SQS nie są jedną transakcją. Zapisz rekord domenowy i outbox w tej samej transakcji; publisher wysyła asynchronicznie.

Praktyka / decyzja projektowa

BEGIN; INSERT orders; INSERT outbox(event_id,payload); COMMIT. Publisher publikuje i oznacza wysyłkę; powtórna publikacja nadal możliwa.

Pytanie senior / pułapka

Inbox/processed_events z UNIQUE(event_id, consumer_name) pozwala bezpiecznie deduplikować.

Zagadnienie 5 / 5

Skalowanie workerów

Przepustowość = concurrency / średni czas zadania, ograniczona zależnościami. Limituj równoległość, batch size i połączenia DB.

Praktyka / decyzja projektowa

Przy napływie 5000/s i przetwarzaniu 3000/s backlog rośnie o 2000/s; kolejka tylko kupuje czas. Skaluj capacity albo ogranicz ingest.

Pytanie senior / pułapka

Na rozmowie odróżnij przyjęcie HTTP 202 po trwałym zapisie w kolejce od potwierdzenia zakończenia operacji.
