Messaging — SQS, SNS, EventBridge i workflow

Semantyka dostarczenia, kolejność, skalowanie i niezawodność

1. SQS: lease zamiast potwierdzenia odbioru

ReceiveMessage zwraca wiadomość i receipt handle konkretnej próby; visibility timeout to czas dzierżawy, nie blokada gwarantująca wyłączność. DeleteMessage używa aktualnego receipt handle, dopiero po durable commicie. Worker, który padnie po commicie przed delete, spowoduje redelivery. Wydłużaj visibility heartbeat'em tylko do sensownego deadline; maksymalny czas widoczności od odbioru to 12 h. Domyślnie 30 s, retention od 1 min do 14 dni (domyślnie 4 dni), long polling do 20 s. Batch API do 10 wiadomości; limit pojedynczej wiadomości to 1 MiB (1 048 576 bajtów); suma payloadów SendMessageBatch również podlega limitowi 1 MiB, duże payloady przechowuj w S3 z referencją i kontrolą retencji. Batch API może zwrócić częściowy sukces nawet z HTTP 200 — retry tylko failed entries.

2. Standard, FIFO, deduplication i head-of-line blocking

Standard dopuszcza duplikaty i zmianę kolejności; FIFO porządkuje wiadomości w ramach MessageGroupId. Deduplikacja producenta obejmuje 5-minutowe okno, content-based dedup hashuje body, nie attributes. Nie gwarantuje to dokładnie jednego skutku ubocznego w DB. Grupa orderId pozwala skalować różne zamówienia; grupa globalna serializuje system. Poison message może zablokować kolejne wiadomości grupy; DLQ może naruszyć semantykę biznesowej kolejności, więc dla wymogu ścisłego porządku zatrzymaj grupę i uzgodnij naprawę. Throughput FIFO zależy od liczby grup, partycji, batchingu, high-throughput mode i Regionu. Sprawdź osobno in-flight quota i API TPS.

3. Worker i backlog

Jeśli napływ 5000/s a wydajność 3000/s, po minucie backlog wzrośnie o 120 000. Po ustaniu ruchu opróżnienie zajmie 40 s; przy stałym napływie 2000/s — 120 s. Zwiększenie liczby workerów działa tylko, gdy downstream ma capacity. Mierz ApproximateAgeOfOldestMessage, visible/not visible, receive/delete rate, DLQ oraz rzeczywisty end-to-end lag. Metryki SQS są przybliżone. Long polling redukuje empty receives. Nie pobieraj więcej niż możesz obsłużyć przed upływem visibility. Lambda event source mapping ma oddzielne max concurrency, batching i partial failure; szczegóły.

4. SNS: fan-out i niezależne granice awarii

OrderPlaced → SNS → SQS billing, analytics, fulfillment. Każdy consumer ma osobną kolejkę i niezależny backlog. Subscription filter na attributes lub body ogranicza routing; zmiana filtra nie musi działać natychmiast. Raw message delivery zmienia envelope: kontrakt konsumenta musi pasować. Polityka kolejki musi zezwolić sns.amazonaws.com na SendMessage z warunkiem aws:SourceArn właściwego topicu; KMS wymaga osobnych uprawnień. Retry SNS dotyczy dostarczenia do subskrypcji i zależy od protokołu; DLQ subskrypcji przechwytuje niedostarczone wiadomości, DLQ kolejki — nieprzetworzone. To dwa różne etapy. FIFO topic + FIFO queue daje kolejność per group, nie end-to-end exactly once.

5. EventBridge i Step Functions

EventBridge routuje zdarzenia według wzorców source/detail-type/detail; reguły i targets są niezależne, nie ma gwarancji kolejności. PutEvents może zwrócić FailedEntryCount mimo HTTP 200; sprawdzaj rezultat per entry. Retry i DLQ targetu dotyczą dostarczenia do targetu, nie sukcesu logiki po asynchronicznym przyjęciu. Archive/replay pozwala odtworzyć zdarzenia, ale może ponowić side effects; consumer musi znać semantykę replay. Step Functions Standard utrzymuje trwałą historię i wspiera długie workflow, callback task token; Express optymalizuje krótkie masowe wykonania, asynchroniczny Express ma at-least-once, synchroniczny at-most-once. Żaden nie gwarantuje exactly-once efektu w zewnętrznym SAP. Retry/Catch, timeout/heartbeat i kompensacja wymagają osobnych reguł. Duże dane trzymaj poza stanem workflow; sprawdzaj limity payload/history w dokumentacji.

6. Outbox i inbox: granica transakcji

Zapis domeny i outbox w jednym commicie. Publisher może używać FOR UPDATE SKIP LOCKED z krótkim claim i lease lub CDC z WAL. Nie trzymaj transakcji podczas sieciowego publish; po publikacji oznacz rekord jako wysłany. Crash przed oznaczeniem = duplikat. Consumer w jednej transakcji wstawia UNIQUE(consumer,event_id), sprawdza czy insert się udał, wykonuje zmianę domeny i commit; dopiero potem ack. Przy zewnętrznym side effect poza DB potrzebujesz idempotency key u dostawcy albo reconciliation, inbox sam nie wystarczy. Retencja klucza dedup musi pokrywać możliwy replay. PostgreSQL.

7. DLQ, redrive i ewolucja eventów

Błąd transient (timeout, 429, 503) retry z exponential backoff i full jitter, permanent (schema mismatch, brak wymaganych danych) kwarantanna, unknown outcome — status/reconciliation. MaxReceiveCount dobierz do czasu odzyskiwania, nie 1. DLQ alarmuj nawet dla jednej krytycznej wiadomości, retention DLQ dłuższa niż source (standard zachowuje original enqueue time). Redrive z kontrolą tempa po naprawie, nie automatyczna pętla. Event envelope: eventId, type, schemaVersion, occurredAt, aggregateId, aggregateVersion, traceId, payload. Additive changes i tolerant readers; event immutable; przy zmianie semantyki nowy typ lub wersja, test kontraktu i plan migracji.

Praktyka: SQS worker i bezpieczny ack

Fragment AWS SDK v3, Standard queue. processAtomically to transakcja inbox + business update, nie transakcja z zewnętrznym API.

const batch = await sqs.send(new ReceiveMessageCommand({
  QueueUrl: queueUrl, MaxNumberOfMessages: 10,
  WaitTimeSeconds: 20, VisibilityTimeout: 60
}));
for (const msg of batch.Messages ?? []) {
  try {
    const event = parseEvent(msg.Body); // stable eventId
    await processAtomically(event);
    await sqs.send(new DeleteMessageCommand({
      QueueUrl: queueUrl, ReceiptHandle: msg.ReceiptHandle
    }));
  } catch (err) {
    logSafeFailure(msg.MessageId, err);
    // no ack; redelivery / configured DLQ
  }
}

Visibility wszystkich wiadomości biegnie od odbioru; przy sekwencyjnym batchu ostatni rekord może już stracić lease. Kontroluj concurrency i maksymalny czas batcha. W FIFO zatrzymaj właściwą sekwencję po błędzie. SNS ma własny limit payloadu, nie zakładaj że 1 MiB przejdzie przez fan-out.

Granice usług i konfiguracja, która zmienia architekturę

Stan dokumentacji AWS: 27.11.2026. Limity konta/Regionu sprawdź przed wdrożeniem. Wartości payload dotyczą konkretnych operacji i trzeba uwzględnić envelope, attributes oraz ograniczenia targetu.

UsługaGranica / konsekwencja
SQS1 MiB wiadomość, do 10 rekordów w batch API; 15 min maksymalnego delivery delay, 12 h visibility, 14 dni retention. Dla dłuższych opóźnień zaplanuj scheduler.
SNSDomyślnie 256 KiB. MaximumMessageSize może zwiększyć limit do 1 MiB, ale przy wartości powyżej 256 KiB topic może mieć najwyżej 100 subskrypcji i tylko obsługiwane targety (SQS, Lambda, Firehose). Weryfikuj rozmiar po dodaniu envelope.
EventBridge PutEventsDo 10 entries, łączny rozmiar poniżej 1 MiB. Throttling per Region; w eu-central-1 dokumentacja podaje 2400 PutEvents TPS (quota adjustable). Classic bus target domyślnie 24 h / 185 retries; nowszy Custom Event Bus ma odrębne defaults — ustaw jawnie.
Step FunctionsStandard do roku, Express do 5 min. Payload 256 KiB na task/state/execution. Standard history max 25 000 eventów; długie pętle mogą wyczerpać limit przed timeoutem.

Przy standardowym SQS Lambda batch może zawierać do 10 000 rekordów (FIFO do 10), jednak limit 6 MB invoke i metadata ogranicza rzeczywisty rozmiar. Batching window dla Standard do 300 s; przy małym ruchu funkcja może czekać dłużej niż bardzo krótki ustawiony window. Reserved concurrency funkcji musi pokrywać sumę maximum concurrency mappings; ustaw osobny cap dla krytycznego downstream. Przy FIFO liczba aktywnych grup może ograniczyć throughput niezależnie od cap.

Step Functions Inline Map wykorzystuje historię parent i ma ograniczoną współbieżność; Distributed Map pozwala czytać większy zbiór z S3 i uruchamiać child workflows, ale ustaw MaxConcurrency zgodnie z downstream. Retry/Catch nie zastępują idempotencji, a timeout callback taska nie cofa zewnętrznej pracy. Task token to sekret; nie umieszczaj go w niezaufanych logach.
