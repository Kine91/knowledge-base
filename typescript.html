TypeScript — type system i kontrakty

Zaawansowane modelowanie stanów, inference, variance, generics i granice runtime

1. Variance i structural typing2. Discriminated unions i type-driven domain3. Generics, mapped i conditional types4. Narrowing, assertions i walidacja5. Biblioteki, module resolution i build6. Testowanie typów i ewolucja

1. Variance i structural typing

Typy są przypisywalne na podstawie struktury, nie nazw. Excess property checking działa głównie dla świeżych object literals, nie jest exact type validation. TypeScript pozwala na pewne niesound przypisania z powodów ergonomii. strictFunctionTypes kontroluje contravariance parametrów funkcji, ale metoda obiektu ma wyjątek bivariance; handler przyjmujący tylko Dog nie jest bezpiecznym handlerem Animal. Zwracane wartości są zwykle covariant. Mutable arrays są źródłem niesoundness (możliwość wstawienia innego podtypu przez alias); ReadonlyArray ogranicza to ryzyko. Typy readonly nie gwarantują runtime immutability ani głębokiej ochrony. Dla SDK publicznego projektuj wąskie wejście i jawny wynik, nie eksportuj przypadkowych typów wewnętrznego ORM.

2. Discriminated unions i type-driven domain

Przykład statusów procesu integracji; typ powinien utrudniać niedozwolone kombinacje danych:
type Job =
  | { status: "PENDING"; id: string }
  | { status: "CONFIRMED"; id: string; sapId: string }
  | { status: "UNKNOWN"; id: string; attemptId: string }
  | { status: "REJECTED"; id: string; reason: string };

function label(job: Job): string {
  switch (job.status) {
    case "PENDING": return "Oczekuje";
    case "CONFIRMED": return job.sapId;
    case "UNKNOWN": return "Wymaga uzgodnienia";
    case "REJECTED": return job.reason;
    default: return assertNever(job);
  }
}
function assertNever(x: never): never {
  throw new Error("Unexpected job state");
}
Po dodaniu nowego statusu kompilator wykryje brak obsługi. Runtime parser musi jednak odrzucić nieznany status lub mapować go do jawnego UNKNOWN; assertNever nie jest walidacją zewnętrznego kontraktu. W DB CHECK/constraints i transakcje chronią stan niezależnie od typów. Branded types stosuj po walidacji, nie przez niekontrolowane as.

3. Generics, mapped i conditional types

Generics utrzymują relacje wejście-wyjście, np. get<K extends keyof T>(key:K):T[K]. Nie dodawaj type parameter, gdy nie przenosi żadnej informacji. Conditional types z infer wydobywają wynik funkcji lub element kolekcji; dystrybucja po union dotyczy naked type variable. Mapped types mogą zmieniać optional/readonly i remapować keys. Przykład event map:
type Events = {
  OrderPlaced: { orderId: string; totalCents: number };
  OrderCancelled: { orderId: string; reason: string };
};
type DomainEvent = {
  [K in keyof Events]: { type: K; payload: Events[K] }
}[keyof Events];
function publish<K extends keyof Events>(
  type: K, payload: Events[K]
) { /* adapter */ }
Mapped discriminated union zachowuje korelację type/payload także po zapisaniu w kolekcji. Generyczne API może przy jawnie szerokim K dopuścić niepożądane kombinacje, więc na granicy serializacji preferuj pojedynczy DomainEvent. satisfies sprawdza zgodność i zachowuje precyzyjny inferred type, as const zawęża literały i readonly. Typy conditional o wielkiej rekursji mogą spowolnić tsc; uprość jeśli koszt przewyższa korzyść.

4. Narrowing, assertions i walidacja

unknown z HTTP/JSON/SQS wymaga schema.parse lub safeParse; parser może transformować input, więc odróżnij input/output type. Type predicates i assertion functions mogą kłamać, kompilator ufa implementacji; testuj je z błędnymi danymi. Truthiness narrowing odrzuca także 0 i pusty string; używaj nullish checks gdy to prawidłowe wartości. Optional chaining nie zastępuje domain validation; ?? zachowuje 0/false. exactOptionalPropertyTypes rozróżnia brak właściwości od undefined; PATCH powinien mieć jawne reguły missing/null. noUncheckedIndexedAccess dodaje undefined dla niezabezpieczonych indeksów. Unikaj wielopoziomowych non-null assertions — modeluj invariant w parserze lub guardzie.

5. Biblioteki, module resolution i build

ESM/CJS: package.json type, exports/imports, .mts/.cts i NodeNext muszą odpowiadać runtime. TS paths nie zmieniają importów emitowanego JS bez bundlera/resolvera; problem widoczny często dopiero w Dockerze/Lambdzie. isolatedModules i verbatimModuleSyntax pomagają z bundlerami, import type nie generuje runtime importu. declaration files opisują publiczny kontrakt, nie implementują walidacji. Project references i incremental builds przyspieszają monorepo, ale wymagają poprawnych granic zależności. Transpile-only narzędzie może nie sprawdzać typów: CI zawsze typecheck. Typowe źródło problemów: dwie wersje biblioteki z różnymi private fields, dependency graph z circular import, runtime enum i decorator metadata zależne od kompilacji. TypeScript nie rozwiązuje circular dependencies samodzielnie.

6. Testowanie typów i ewolucja

Testy compile-time (np. expectTypeOf, tsd lub @ts-expect-error) utrwalają publiczne typy: błędny payload ma nie przejść kompilacji, prawidłowy zachowuje inference. @ts-expect-error przestanie przechodzić, gdy błąd zniknie; @ts-ignore ukrywa problem bez sygnału. Dla biblioteki dodanie wymaganej właściwości, zawężenie input union lub rozszerzenie output union może być breaking change. Testuj public API w rzeczywistym consumer project, nie tylko w source package. Generowane DTO synchronizuj z wersjonowanym OpenAPI, a runtime testy z fixtures. Runtime Node.js · Domain modeling.
