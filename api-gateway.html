API Gateway — ingress, throttling i integracje

REST/HTTP/WebSocket API, autoryzacja, limity i awarie

1. REST API vs HTTP API vs ALB

HTTP API wybierz dla prostego routingu HTTP, JWT authorizer i niskiego narzutu. REST API ma dodatkowe mechanizmy (np. usage plans, request validation, private endpoints, WAF); sprawdź bieżącą macierz funkcji. ALB naturalnie pasuje do długotrwałych kontenerów i health checks, a CloudFront do edge caching. WebSocket API utrzymuje connectionId zarządzany przez Gateway, nie przez Lambdę; $connect, $disconnect i routes są oddzielnymi zdarzeniami, a push wymaga Management API. Połączenie może zniknąć przed wysłaniem: obsłuż Gone i sprzątaj rejestr połączeń.

2. Token bucket i quota

Rate to tempo uzupełniania tokenów, burst to pojemność kubełka. Każde żądanie zużywa token. Domyślna regionalna quota konta wynosi zwykle 10 000 RPS i burst 5000, z wyjątkami regionalnymi; jest współdzielona między typami API. Stage/route throttles i usage plans są best effort, nie gwarancją izolacji ani mechanizmem billingowym. 429 z Retry-After jeśli dostępny; klienci retry z jitterem. Ogranicz również concurrency aplikacji, bo 1000 RPS może oznaczać bardzo różną liczbę in-flight żądań. WAF/rate-based rules redukują nadużycia, ale nie zastępują limitów per tenant w aplikacji.

3. Timeouty, payload i mapping

HTTP API ma maksymalny integration timeout 30 s; REST API standardowo 29 s, Regional/private mogą mieć podwyższony limit kosztem regionalnego throttle quota. Payload API typowo 10 MB, ale Lambda proxy ma własny limit wejścia synchronicznego 6 MB, a base64 zwiększa rozmiar ok. 33%. Ograniczenie ścieżki jest minimum limitów wszystkich ogniw. Gateway 504 nie cofa skutku ubocznego w backendzie. Ustaw budżet np. klient 8 s, gateway 6 s, handler 5 s, downstream 3 s (wartości przykładowe). Długą operację przyjmij jako 202 + status resource, nie zwiększaj timeoutów w nieskończoność. HTTP API payload format 1.0/2.0 różni się reprezentacją headers, cookies i path; waliduj adapter.

4. Authorization i cache

JWT authorizer weryfikuje podpis, issuer, audience/scopes zgodnie z konfiguracją; aplikacja nadal sprawdza ownership zasobu. Nie traktuj API key jako tożsamości użytkownika. Lambda authorizer z cache może zwrócić policy zbyt szeroką dla innej trasy: dobierz identity sources i zakres policy (np. route key w cache key tam, gdzie wspierane). Dla CORS nie używaj wildcard origin z credentials; preflight OPTIONS musi działać niezależnie od auth tam, gdzie wymagane. Zabezpiecz również bezpośrednią ścieżkę do backendu i wyłącz niepotrzebny default endpoint.

5. Integracja prywatna i diagnostyka

VPC Link pozwala łączyć gateway z prywatnym backendem; wspierane targety zależą od rodzaju API (ALB/NLB/Cloud Map). Security groups i routing nadal obowiązują. Porównuj Latency (całość w gateway) z IntegrationLatency (czas backendu), loguj request ID, route, status i integration error. 502 często wynika z niepoprawnego formatu odpowiedzi proxy lub błędu integracji, 504 z timeoutu, 429 z throttlingu; nie diagnozuj wyłącznie na podstawie statusu. Deployment stage i custom domain mapping muszą wskazywać właściwe środowisko. Przykład kontraktu błędu: {code:"ORDER_CONFLICT",requestId:"...",retryable:false}; nie zwracaj stack trace.

Praktyka: kontrakt Lambda proxy

HTTP API payload v2.0: jednoznaczny status, headers i body. 202 dopiero po trwałym przyjęciu operacji, nie po zapisaniu w RAM.

return {
  statusCode: 202,
  headers: {
    "content-type": "application/json",
    "location": "/operations/" + operationId
  },
  body: JSON.stringify({ operationId, status: "PENDING" })
};

Gdy outcome zapisu jest nieznany, retry z tym samym idempotency key. Gateway i backend mają oddzielne alarmy na throttling. Nie loguj tokenów ani body z PII.
