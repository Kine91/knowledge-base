DynamoDB, Redis i Kafka — modele i kompromisy

Porównanie alternatyw dla PostgreSQL/SQS: partycjonowanie, cache i log zdarzeń

1. DynamoDB access patterns i hot partitions2. DynamoDB consistency, capacity, GSI i transakcje3. Redis: cache, eviction i concurrency4. Kafka: log, partition, consumer group5. Wybór SQS vs Kafka i Postgres vs DynamoDB

1. DynamoDB access patterns i hot partitions

Modeluj od zapytań: partition key rozkłada ruch, sort key umożliwia zakres i uporządkowanie w ramach PK. Query wymaga PK equality, Scan czyta wiele partycji; FilterExpression działa po odczycie i nie redukuje read capacity. Przykład PK=TENANT#id, SK=ORDER#timestamp#id, ale bardzo duży tenant może stać się hot key. Write sharding (np. bucket 0..15) rozkłada obciążenie kosztem fan-out read i merge. Partycja ma granice throughput (dokumentacja podaje 3000 RCU i 1000 WCU/s), adaptive capacity nie usuwa wszystkich hot-key limitations. On-demand nie oznacza nieskończonego burstu. Item max 400 KB; większe dane w S3 z referencją. Projektuj cardinality, item size i access patterns przed wyborem single-table design.

2. DynamoDB consistency, capacity, GSI i transakcje

Strong read na wspieranych base table/LSI, GSI eventual consistency; po zapisie query GSI może nie widzieć elementu. W typowym modelu 1 WCU = zapis do 1 KB/s, 1 RCU = strong read do 4 KB/s, eventual read zużywa połowę (zaokrąglaj rozmiary, transakcje kosztują więcej). 2.5 KB item write = 3 WCU; projekcja GSI może dodawać osobny write cost, hot GSI może throttle base table. Conditional expression attribute_not_exists(PK) lub version comparison chroni przed overwrite; TransactWriteItems zapewnia atomowość obsługiwanych operacji w Regionie, nie w SAP. TTL deletion jest asynchroniczne: wygasły rekord nadal może zostać odczytany, filtruj expiry w aplikacji. BatchGet/BatchWrite mogą zwrócić unprocessed items mimo sukcesu requestu; retry z backoff. Dla global tables sprawdź konkretny consistency mode, nie zakładaj uniwersalnej eventual consistency.

3. Redis: cache, eviction i concurrency

Redis to pamięciowy data store; większość komend wykonuje się sekwencyjnie na shardzie, długi Lua/script lub ciężkie KEYS może blokować inne operacje. SCAN iteruje bez snapshot guarantee. Pipeline redukuje RTT, nie jest transakcją. MULTI/EXEC grupuje polecenia bez rollback w przypadku runtime error; WATCH umożliwia optimistic CAS. Cache-aside z TTL jitter, single-flight i negative cache; monitoruj hit ratio wraz z downstream load, memory, evicted_keys, latency i hot keys. maxmemory policy (allkeys-lru/lfu, volatile, noeviction) dobierz do przeznaczenia; cache i trwałe joby nie powinny współdzielić eviction policy. RDB/AOF i async replication mają własne okna utraty; WAIT nie zmienia Redis w silnie spójną DB. Cluster hash slots rozkładają klucze, multi-key operations wymagają zgodnego slotu (hash tags). Distributed lock SET NX PX + unikalny token i atomowy compare/delete chroni przed usunięciem cudzej dzierżawy, ale expired lease nie powstrzyma spóźnionego klienta; dla correctness potrzebny fencing/DB constraint.

4. Kafka: log, partition, consumer group

Kafka zachowuje rekordy według retencji/compaction niezależnie od odczytu. Partition wyznacza porządek, key wybiera partycję; consumer group dzieli partycje między aktywnych consumerów, więc liczba partycji ogranicza równoległość w klasycznym modelu. Offset to pozycja konsumenta, commit przed side effect ryzykuje utratę pracy, commit po side effect daje duplikaty. Rebalance może przerwać ownership, worker nie powinien commitować offsetu za nieukończone wcześniejsze rekordy. Poll/heartbeat/max poll interval zależą od klienta, długie przetwarzanie wymaga świadomego pause/resume i bounded concurrency. Producer acks=all + min.insync.replicas daje kontrolę durability; utrata wymaganej liczby replik oznacza niedostępność zapisów, nie magiczną gwarancję. Idempotent producer redukuje duplikaty retry w zakresie protokołu; Kafka transactions zapewniają atomic read-process-write do Kafka z offsetami, nie transakcję z Postgres/SAP. read_committed pomija aborted records; zewnętrzne efekty potrzebują inbox/outbox.

5. Wybór SQS vs Kafka i Postgres vs DynamoDB

SQS: work queue z per-message ack, prosty scaling i DLQ; Kafka: log do replay, wielu consumer groups, porządek per partition, większa złożoność operacyjna i kontrakt retencji. SNS/EventBridge fan-out/routing nie zastępuje logu z consumer offsets. PostgreSQL: relacje, constraints, ad hoc SQL, transakcje wielu tabel; DynamoDB: z góry znane access patterns i skalowanie przez partycjonowanie, koszt denormalizacji/secondary indexes. Redis cache skraca odczyt, nie wybieraj go jako source of truth bez zdefiniowanej durability. Decyzja na podstawie workload, SLO, operacyjności i gwarancji consistency, a nie popularności usługi.
