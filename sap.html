SAP — integracja systemów enterprise

Kontrakty, protokoły, business consistency, reconciliation, bezpieczeństwo

1. Własność danych i wybór interfejsu

SAP S/4HANA, ECC i usługi BTP mogą mieć odmienne interfejsy i ograniczenia. Nie zakładaj konkretnej wersji ani protokołu. OData/REST udostępnia zasoby, SOAP kontrakt WSDL, RFC/BAPI wywołuje funkcje SAP, IDoc często przenosi dokumenty asynchronicznie przez middleware. Uzgodnij z zespołem SAP dostępne released APIs, sandbox, SLA, maintenance windows, batch limits, ownership master data i semantykę statusów. SAP może być source of truth dla materiałów/stanów/księgowań, aplikacja dla intencji użytkownika. Unikaj bezpośredniego zapisu do tabel SAP. Anti-corruption layer izoluje kontrakt zewnętrzny, nie usuwa różnic domenowych.

2. OData, SOAP, RFC/BAPI, IDoc — niuanse

OData: $select/$filter/$expand ograniczają payload, ale złożony expand może kosztować SAP dużo pracy; server-driven paging używa nextLink, nie konstruuj go na ślepo. ETag/If-Match do optimistic concurrency gdy endpoint wspiera. Niektóre SAP OData write APIs wymagają CSRF tokenu pobranego z odpowiednim session cookie; to zależne od systemu i auth. $batch może grupować requesty, changeset ma określoną atomowość według kontraktu. SOAP: XML namespaces, fault envelope i WSDL/versioning; HTTP 200 nie musi oznaczać sukcesu biznesowego. RFC/BAPI: sprawdź RETURN messages i wymagane COMMIT/ROLLBACK WORK (np. BAPI_TRANSACTION_COMMIT tylko gdy kontrakt tego wymaga), nie zakładaj że transport success zatwierdza dokument. IDoc: techniczne przyjęcie vs processing status vs business posting; monitoring statusów i reprocessing po stronie SAP. Nie implementuj protokołów własnoręcznie bez uzgodnionej biblioteki/middleware.

3. Model domenowy, mapowanie i precyzja

Canonical command: orderId, tenant, items, quantity, unit, currency, amount, externalReference, schemaVersion. Mapping kodów materiałów, jednostek, company code i plant powinien być wersjonowany i testowany fixture'ami od SAP. Zachowaj leading zeros identyfikatorów; decimal/string zamiast JS float dla ilości i pieniędzy; reguły rounding i currency decimals uzgodnij. Daty lokalne i timestamp UTC to różne typy. Puste stringi, null i brak pola mogą mieć różną semantykę. Nie zapisuj raw response z PII bez retencji/redaction. Utrzymuj audit: external reference, attemptId, status i correlationId. Zmiana mappingu nie powinna zmieniać historycznych dokumentów przy replay bez jawnej decyzji.

4. Reliable delivery i unknown outcome

Orders zapisuje lokalną intencję i outbox, SQS worker wysyła command z deterministycznym externalReference. State machine: PENDING → SENDING → CONFIRMED/REJECTED/UNKNOWN; UNKNOWN po timeout/reset, bo dokument mógł powstać. Przed ponownym create sprawdź status po externalReference lub użyj idempotency mechanizmu wspieranego przez SAP. Sam UNIQUE lokalnie nie gwarantuje braku duplikatu w SAP. Jeśli nie ma reliable lookup ani idempotency, wstrzymaj automatyczny replay i skieruj do uzgodnienia. Dla business reject nie retryuj bez zmiany danych; 429/5xx/backoff według kontraktu. Limituj concurrency per SAP endpoint/tenant; circuit breaker i kolejka izolują awarię. Kolejność per aggregate może być wymagana dla create/update/cancel. SQS/outbox.

5. Reconciliation, monitoring i runbook

Okresowo porównuj lokalne dokumenty z SAP według zewnętrznego ID, wersji i statusu. Wykrywaj missing/duplicate/mismatch, rozróżnij opóźnienie od niespójności; osobna ścieżka manual review z audytem. Reconciliation nie powinno bezwarunkowo nadpisywać source of truth. Dashboard: accepted, confirmed, rejected, unknown, oldest pending, retry count, SAP latency p95/p99 i status errors. Runbook: wstrzymaj consumer, zidentyfikuj partię, sprawdź status SAP, napraw mapping, testuj pojedynczą wiadomość, ograniczony redrive, monitoruj lag. Replay musi zachować stable business ID. Ustal odpowiedzialność L1/L2 i zespołu SAP, ścieżkę eskalacji w maintenance windows.

6. Networking, auth i testy kontraktu

On-prem SAP: VPN/Direct Connect lub zatwierdzony integration runtime, DNS, certyfikaty, firewall i redundant path; SAP Cloud Connector to specyficzne rozwiązanie w ekosystemie BTP, nie uniwersalny proxy. Auth zależny od API (OAuth client credentials, mTLS, technical user); secrets rotation, least privilege, segregacja uprawnień do księgowań. Uzgodnij cert expiry i retry po reconnect. Testy: mapping fixtures, consumer contract, sandbox smoke, throttling, częściowe sukcesy, unknown outcome po commicie SAP, replay i schema drift. Mock nie potwierdza semantyki BAPI commit ani realnych limitów; testy na zatwierdzonym środowisku są niezbędne.

Praktyka: trwały model retry i reconciliation

CREATE TABLE sap_operations (
  operation_id uuid PRIMARY KEY,
  external_ref text NOT NULL UNIQUE,
  state text NOT NULL CHECK (state IN
    ('PENDING','SENDING','RETRY','UNKNOWN','CONFIRMED','REJECTED')),
  sap_document_id text,
  attempts integer NOT NULL DEFAULT 0,
  updated_at timestamptz NOT NULL DEFAULT now(),
  next_attempt_at timestamptz
);

To fragment modelu; claim wymaga atomowej zmiany stanu i lease. Jeśli worker umrze w SENDING, po wygaśnięciu lease przejdź do UNKNOWN, nie RETRY. Po wyniku biznesowym zapisz SAP ID i status. Lookup external_ref przed retry jest bezpieczny tylko gdy kontrakt pozwala wykluczyć późny zapis. Lokalny UNIQUE nie wymusza unikalności SAP. Uzgodnij partial success, cancel/reversal i odpowiedzialność operatora.
