Clean Code i Design Patterns

SOLID, modularność, kompromisy

1. Dependency inversion2. Strategy i Factory3. Adapter i Anti-Corruption Layer4. Review i utrzymanie
Zagadnienie 1 / 4

Dependency inversion

Use case zależy od portu (np. OrderRepository), adapter Postgres implementuje kontrakt. Testujesz logikę niezależnie od frameworka.

Praktyka / decyzja projektowa

interface OrderRepo { save(order:Order):Promise<void> }; class PlaceOrder { constructor(private repo:OrderRepo){} }

Pytanie senior / pułapka

Nie twórz interfejsu dla każdej klasy bez potrzeby wymienności lub testowania granic.

Zagadnienie 2 / 4

Strategy i Factory

Strategy pozwala podmienić zachowanie (np. kalkulacja wysyłki), Factory izoluje wybór i konstrukcję implementacji. W TS często wystarczy mapa funkcji.

Praktyka / decyzja projektowa

const calculators = {standard: calcStandard, express: calcExpress}; sprawdź exhaustiveness dla union type.

Pytanie senior / pułapka

Preferuj prosty kod nad hierarchią klas, jeśli problem jest mały.

Zagadnienie 3 / 4

Adapter i Anti-Corruption Layer

Integracja SAP ma własny model i niestabilności. Adapter tłumaczy protokół i DTO do pojęć domenowych, ogranicza zależność systemu od SAP.

Praktyka / decyzja projektowa

SAP MaterialCode → własne ProductId; błędy techniczne SAP mapuj na retryable/non-retryable, nie przepuszczaj raw payload głęboko w domenę.

Pytanie senior / pułapka

Nie udawaj, że ACL eliminuje konieczność ustalenia semantyki biznesowej pól.

Zagadnienie 4 / 4

Review i utrzymanie

W review sprawdzaj invariants, testy graniczne, obserwowalność, kompatybilność API, migracje i bezpieczeństwo; nazwy są wtórne względem correctness.

Praktyka / decyzja projektowa

Checklist: czy retry tworzy duplikaty? czy transakcja ma granice? czy log nie ujawnia PII? co przy timeout?

Pytanie senior / pułapka

Kompromisy dokumentuj ADR: kontekst, alternatywy, decyzja, konsekwencje.
