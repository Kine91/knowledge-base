Clean Code, Design Patterns i architektura kodu

SOLID w praktyce, dependency direction, wzorce domenowe i refactoring

1. SOLID jako heurystyki, nie rytuał2. Hexagonal / Clean Architecture i DDD3. Strategy, Factory, Adapter, Decorator4. State, Command, Observer, Chain of Responsibility5. Wzorce rozproszone i koszt abstrakcji6. Refactoring, code review i ADR

1. SOLID jako heurystyki, nie rytuał

SRP: jeden powód zmiany wynikający z odpowiedzialności, nie jedna metoda na klasę. OCP: stabilny punkt rozszerzenia dla realnej zmienności, nie przewidywanie hipotetycznych potrzeb. LSP: podtyp zachowuje kontrakt (pre/postconditions, invariants, wyjątki); repository fake zwracający zawsze sukces może łamać semantykę realnego repo. ISP: interface z perspektywy konsumenta, nie god interface. DIP: polityka domenowa zależy od portu, adapter implementuje port. Dependency injection to technika, inversion to kierunek zależności. DRY dotyczy jednej wiedzy biznesowej, nie każdego podobnego fragmentu; przedwczesne wspólne abstrakcje spinają niezależne domeny. Preferuj kompozycję i pure functions, stosuj klasy gdy encja chroni invariant lub dependency lifecycle.

2. Hexagonal / Clean Architecture i DDD

Domena nie importuje AWS SDK, HTTP, ORM ani UI. Application use case koordynuje transakcje/porty, adapter mapuje DTO i wyjątki. Encja Order zachowuje identity i pilnuje state transitions; value object Money waliduje currency i jednostki; aggregate jest granicą consistency, nie całym grafem encji. Repository zwraca model domenowy lub jawny read projection; Unit of Work wyznacza transaction boundary, nie ukrywa I/O. Prosty CRUD nie wymaga pełnego DDD; przy złożonych regułach koszt odseparowania jest uzasadniony.
interface OrderRepository {
  get(id: OrderId): Promise<Order | null>;
  save(order: Order, expectedVersion: number): Promise<void>;
}
class ConfirmOrder {
  constructor(private readonly orders: OrderRepository) {}
  async execute(id: OrderId) {
    const order = await this.orders.get(id);
    if (!order) throw new NotFoundError();
    const version = order.version;
    order.confirm(); // invariant inside domain
    await this.orders.save(order, version); // optimistic CAS
  }
}
Adapter mapuje konflikt wersji, use case decyduje czy retry jest bezpieczne. Dla zmiany + eventu w jednej DB potrzebny Unit of Work/outbox.

3. Strategy, Factory, Adapter, Decorator

Strategy oddziela algorytm od wyboru: Record<ShippingType, Calculator> lub funkcje first-class zamiast dziedziczenia. Factory centralizuje konstrukcję i wybór implementacji, composition root konfiguruje zależności. Adapter mapuje protokół i semantykę zewnętrznego systemu, Facade upraszcza API kilku komponentów. Decorator/wrapper dodaje metryki, cache, retry lub auth bez modyfikacji use case; kolejność istotna: retry na zewnątrz logowania attemptów daje inne metryki niż odwrotnie. Nie retryuj nieidempotentnych metod przez generyczny dekorator. Proxy kontroluje dostęp do obiektu, ale może ukrywać koszt sieci. W TS nie wymuszaj wzorców GoF z Javy, jeśli wystarczy prosty higher-order function.

4. State, Command, Observer, Chain of Responsibility

State machine jawnie definiuje stany, transitions i niedozwolone przejścia; union types zapobiegają kombinacjom flag. Command reprezentuje intencję (CancelOrder), event fakt (OrderCancelled); command ma właściciela i oczekiwany rezultat. Observer/event emitter w procesie nie jest durable pub/sub — awaria gubi event, listener może rzucić błąd, cleanup zapobiega memory leak. Chain of Responsibility (middleware) działa dla pipeline auth/validation/routing; kontroluj kolejność, short-circuit i error handling. Template Method przez inheritance utrudnia wymianę kroków; często pipeline funkcji czytelniejszy. Singleton w DI nie jest globalnym singletonem rozproszonym i nie nadaje się do per-request mutable state.

5. Wzorce rozproszone i koszt abstrakcji

Outbox, inbox, saga, CQRS, cache-aside, circuit breaker, bulkhead, retry, strangler to wzorce architektury, nie mechaniczne klasy. Ustal failure model, invariants i ownership przed wyborem. Distributed lock na Redis wymaga lease, a przy operacjach nieodwracalnych fencing token chroniący przed spóźnionym właścicielem; DB atomic update/unique constraint często prostsze. Idempotency nie jest równoznaczna z dedup cache — trwały skutek musi być atomowy z zapisem klucza. CQRS może działać w jednej DB. System design · Messaging.

6. Refactoring, code review i ADR

Refactor zachowuje zachowanie; characterization tests przed zmianą legacy, małe PR, feature flag i metryki przed/po. Nie mieszaj masowego formatowania z logiką biznesową. Review w kolejności: correctness/invariants, security, concurrency/transactions, failure paths, compatibility/migrations, performance, maintainability, testy. Uwagi oznacz jako blocking vs suggestion, wyjaśnij ryzyko i alternatywę. ADR: context, decision, alternatives, consequences i status; decyzja może być odwracalna lub kosztowna. Nie traktuj coverage ani lintera jako substytutu review. Dług techniczny dokumentuj jako konkretne ryzyko/koszt, nie listę nieładnych klas.
