Case study: system zamówień

Architektura łącząca rozdziały; założenia są ilustracyjne, nie pomiary produkcji.

1. Wymagania i granice

API przyjmuje zamówienia z ruchu burst do 5000 RPS. PostgreSQL przechowuje Orders i trwały outbox; Inventory i SAP mają odrębne granice. Przyjęcie nie oznacza potwierdzenia w SAP. Przykładowe SLO: 99.9% przyjęć w 300 ms, 99% potwierdzeń w 60 s przy zdrowych zależnościach. Tolerowany lag i sposób pomiaru uzgodnij przed projektem.

React → API Gateway → Orders Lambda / ECS
                           ↓
                     PostgreSQL + Outbox
                           ↓
                      SNS / SQS
                     ↙         ↘
           Inventory worker    SAP worker
                     ↘         ↙
                  workflow / projection

2. Przepustowość i izolacja

Przy occupancy DB 20 ms i 5000 RPS potrzeba średnio 100 connections. Z 500 max DB connections zostaw np. 50 reserve, 100 workers, 350 API. Dla ECS 20 tasków podczas rolling max 40 × pool=8 = 320. Limit zweryfikuj load testem: CPU/locks mogą ograniczyć throughput wcześniej. Dla Lambda reserved concurrency i RDS Proxy kontrolują churn, nie zastępują limitu SQL. Jeśli SAP może przetworzyć 100/s, ustaw osobny worker cap; długotrwały ruch powyżej 100/s wymaga zmiany SLA/ingest/capacity.

Backpressure · Pooling · Concurrency.

3. Invariants i durable acceptance

POST /orders z Idempotency-Key; transakcja: request key + order PENDING + outbox. 201 po utworzeniu order resource albo 202 gdy przyjęto jedynie intencję do trwałego przetworzenia. Worker ack po commicie. Inventory atomowo rezerwuje; payment/SAP używają stable business ID. Saga zapisuje UNKNOWN, kompensację i deadline. UI pokazuje status przez polling lub WebSocket z resync.

Idempotency · Outbox · Reconciliation · State.

4. Macierz awarii

AwariaSkutek i reakcja
DB down przed commitemNie potwierdzaj zapisu, ogranicz intake, bezpieczny retry po odzyskaniu.
DB commit, response lostUnknown outcome, ten sam klucz zwraca poprzedni rezultat.
Publisher crash po sendDuplikat eventu, inbox chroni lokalny skutek.
SAP timeout po zatwierdzeniuUNKNOWN, status lookup/reconciliation, bez blind retry.
Poison eventDLQ/alert, naprawa kontraktu, kontrolowany replay.
Rolling deploymentKompatybilność kontraktów, drain, capacity overlap, rollback bez destrukcyjnej migracji.

5. Security, testy i operacje

JWT resource auth per tenant, IAM least privilege, RDS private subnets, KMS/secrets rotation, PII redaction. Test concurrency w realnym PG, crash po commicie przed ack, partial failures, timeout SAP, cold/warm capacity i open-loop load. Alarmy na SLO, age, DLQ, Lambda throttles i pool wait. Dashboard accepted → confirmed/rejected/unknown; traces z eventId, business IDs w logach.

Security · Testing · Runbooks.
