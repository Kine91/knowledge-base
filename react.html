React — rendering, state i architektura frontendu

Mechanika renderowania, concurrency, efekty, stan, performance, bezpieczeństwo i dostępność

1. Render i commit, reconciliation, identity

Render jest obliczeniem drzewa UI, commit stosuje zmiany do DOM. Render powinien być czysty, może zostać przerwany, powtórzony lub odrzucony; nie wykonuj network calls ani mutacji globalnych w renderze. Fiber pozwala planować pracę według priorytetu, ale commit DOM jest synchroniczny. State jest przypisany do pozycji/typu/key w drzewie; zmiana key resetuje subtree, index jako key przy reorder powoduje przypisanie stanu do złego elementu. Komponent definiowany wewnątrz renderu rodzica dostaje nową tożsamość typu i może się remountować. Re-render nie oznacza automatycznie DOM mutation. StrictMode w dev wykrywa brak czystości i cleanup przez dodatkowe wykonania, nie jest odpowiednikiem produkcyjnego podwójnego renderu.

2. Scheduling, state snapshot i batching

Handler widzi snapshot stanu z renderu, w którym powstał. setCount(count+1) trzy razy nie oznacza +3; functional update setCount(c=>c+1) komponuje kolejkę. Automatic batching grupuje wiele aktualizacji, także asynchronicznych w nowoczesnym React; flushSync to awaryjne wymuszenie commit, nie zwykła optymalizacja. startTransition/useTransition oznaczają aktualizacje niepilne; nie opóźniaj controlled input state, wydziel ciężki wynik. useDeferredValue pozwala pokazać starszy wynik podczas renderowania nowego, nie jest debounce ani rate limiterem API. Suspense pokazuje fallback dla obsługiwanych zasobów, granice dobieraj tak, by nie ukrywać całego UI przy zmianie fragmentu. Render concurrent nie oznacza wielowątkowego JS.

3. Effects, stale closure i external stores

useEffect synchronizuje React z zewnętrznym systemem; derived state obliczaj podczas renderu, akcje użytkownika w handlerze. Dependencies porównywane przez Object.is, nowe obiekty/funkcje mogą ponownie uruchamiać efekt. Nie wyłączaj exhaustive-deps dla ukrycia stale closure; zredukuj zależności poprzez przeniesienie logiki lub functional updates. Cleanup przed następnym efektem i unmount; abort request + guard stale response, unsubscribe event listener tą samą referencją. useLayoutEffect blokuje paint, używaj gdy pomiar DOM musi nastąpić przed renderem przeglądarki. useSyncExternalStore daje spójny snapshot zewnętrznego store podczas concurrent render; snapshot musi być cache'owany, gdy stan się nie zmienił.
useEffect(() => {
  const controller = new AbortController();
  let active = true;
  load(id, controller.signal).then(data => {
    if (active) setData(data);
  }).catch(error => {
    if (active && !controller.signal.aborted) setError(error);
  });
  return () => { active = false; controller.abort(); };
}, [id]);
To mechanika przykładowa, nie zamiennik query cache. Abort nie gwarantuje cofnięcia operacji na backendzie.

4. Server state vs client state

TanStack Query zarządza cache według queryKey obejmującego tenant, filters, pagination i wszystkie parametry wpływające na wynik. staleTime to czas uznania danych za świeże, gcTime czas usunięcia nieaktywnego query (nazwy w v5); refetch, retry i invalidation dobieraj do domeny. Współdzielenie queryKey deduplikuje zapytania, ale błędny klucz może mieszać dane użytkowników. Przy logout usuń cache właściwego scope. Optimistic mutation: cancelQueries, snapshot, update, rollback, invalidate; równoległe mutacje mogą nadpisać sobie rollback, użyj wersji lub serializacji per entity. Zustand selector ogranicza subskrypcję do wybranej części, equality przy obiektach zależy od konfiguracji. Context value zmienione referencyjnie re-renderuje subskrybentów; rozdziel state/dispatch i domeny. URL jest właściwym stanem filtrów nawigacyjnych. Nie kopiuj query cache do Redux/Zustand.

5. Performance: od pomiaru do optymalizacji

React Profiler wskazuje koszt renderów i przyczynę aktualizacji; browser Performance panel wskazuje long tasks, layout/paint, network i main thread. Web Vitals: LCP (ładowanie), INP (reaktywność), CLS (stabilność layoutu), analizuj real user monitoring, nie tylko Lighthouse lab. Memo porównuje props płytko, useMemo/useCallback pomagają jeśli koszt obliczenia/referencja ma wpływ; comparator może być droższy niż render i zamknąć stale closure. State colocation, selektory, virtualized lists i pagination często dają więcej niż memoizacja wszystkiego. Virtualizacja wymaga obsługi focus, wysokości wierszy i accessible navigation. Code splitting per route, lazy, preload krytycznych chunków; waterfall network diagnozuj w trace. Layout thrash to naprzemienne odczyty i zapisy DOM; grupuj pomiary. Ciężkie CPU przenieś do Web Worker jeśli koszt komunikacji uzasadniony.

6. SSR, hydration, RSC i granice bundle

SSR generuje HTML, hydration podłącza event handlers i odtwarza oczekiwane drzewo; mismatch z Date.now, Math.random, locale, browser-only APIs lub różnymi danymi powoduje problemy. Server Components wykonują się po stronie serwera w obsługującym frameworku (np. Next.js), nie mogą używać client state/effects; Client Components mogą być prerenderowane na serwerze, więc 'use client' nie oznacza wyłącznie browser execution. Granica serializacji props i bundle; sekret nigdy nie może zostać wysłany do client payload. Cache server/fetch zależy od frameworku i wersji, nie traktuj prywatnych danych jak globalnego cache. Streaming SSR z Suspense redukuje waterfall, ale dobierz fallback i error boundaries. CSR pasuje do zalogowanego narzędzia z ograniczoną potrzebą SEO; SSR nie jest automatycznie szybsze, mierz TTFB, hydration i INP.

7. Architektura, dostępność i bezpieczeństwo

Feature modules (orders, inventory) z publicznym API, shared UI bez zależności domenowych, boundary lint w monorepo. Unikaj megastore i globalnych event busów; dependency direction feature→shared. Microfrontend ma sens przy niezależnym ownership/deploy, lecz kosztuje kontrakty, wspólny React singleton, wersje, routing, CSS isolation i observability; nie dziel wyłącznie według ekranów. Responsywność: CSS grid/flex, container/media queries, ograniczenia min-width i overflow; obsługuj keyboard, focus restore, label i screen reader. XSS: React escapuje tekst, nie zabezpiecza dowolnego HTML/URL; sanitization przy dangerouslySetInnerHTML i CSP. HttpOnly Secure SameSite cookies ograniczają kradzież tokenu przez JS, ale XSS może nadal wykonywać akcje i potrzebna jest ochrona CSRF. CORS nie jest auth. Token refresh single-flight, unikaj infinite retry 401; przy 403 nie odświeżaj bez powodu. Backend contracts.
