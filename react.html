React i frontend architecture

Renderowanie, performance, stan, integracja z API

1. Granice stanu2. Render performance3. Race conditions i UX4. Bezpieczeństwo frontendu
Zagadnienie 1 / 4

Granice stanu

Rozdziel server state (TanStack Query), UI/client state (Zustand/Context) i stan URL. Cache API nie powinien być ręcznie dublowany w global store.

Praktyka / decyzja projektowa

Lista zamówień: queryKey ['orders',filters], staleTime zależny od domeny, invalidacja po mutacji lub aktualizacja cache z ostrożnością.

Pytanie senior / pułapka

Nie używaj useEffect do ręcznego fetchowania każdej listy, gdy potrzebujesz cache/retry/dedup.

Zagadnienie 2 / 4

Render performance

Profiluj React DevTools przed memoizacją. Re-rendery nie zawsze są problemem; koszt DOM, list i computation często dominuje.

Praktyka / decyzja projektowa

Duża tabela: virtualization, stabilne key, paginacja po stronie API, selektory stanu, code splitting per route.

Pytanie senior / pułapka

useMemo/useCallback nie są uniwersalnym rozwiązaniem; zależności i koszt memoizacji mają znaczenie.

Zagadnienie 3 / 4

Race conditions i UX

W wyszukiwaniu użyj debounce, AbortSignal, identyfikacji zapytania w cache. Zapewnij loading/error/empty, retry i optimistic update tylko gdy umiesz cofnąć zmianę.

Praktyka / decyzja projektowa

Formularz edycji: walidacja lokalna i serwerowa; 409 przy konflikcie wersji; zablokuj duplikaty submit, ale nie zakładaj, że to wystarczy backendowi.

Pytanie senior / pułapka

A11y: semantyczne formularze, keyboard navigation, focus management, aria-live dla ważnych statusów.

Zagadnienie 4 / 4

Bezpieczeństwo frontendu

Frontend nie jest zaufaną granicą autoryzacji. Unikaj XSS przez niebezpieczny HTML, nie przechowuj wrażliwych sekretów w bundlu.

Praktyka / decyzja projektowa

HTTP-only secure cookies mogą redukować ekspozycję tokenu na JS, lecz wymagają przemyślanej ochrony CSRF i CORS.

Pytanie senior / pułapka

Sekrety AWS nigdy nie trafiają do frontendu; używaj presigned URL lub backend proxy.
