Backend API — protokoły, bezpieczeństwo i correctness

Idempotency, kontrakty HTTP, autoryzacja, race conditions i niezawodność

1. HTTP semantics, concurrency i błędy2. AuthN, AuthZ, OAuth/OIDC3. Security boundaries i validation4. Idempotent create — transakcja i kontrakt5. REST, gRPC i WebSocket operacyjnie6. Rate limiting i kontrola zasobów

1. HTTP semantics, concurrency i błędy

Idempotent method oznacza taki sam zamierzony efekt wielokrotnego wywołania, nie identyczną odpowiedź (DELETE może zwrócić 204, potem 404). Dla POST payment/order potrzebny idempotency key scope per tenant/operation i durable result. ETag i If-Match pozwalają odrzucić zmianę na nieaktualnej wersji (412), If-None-Match daje 304 dla odczytu; business conflict 409. PATCH JSON Merge Patch i JSON Patch różnią się semantyką null i tablic; ustal content type i kontrakt. 202 oznacza accepted, nie completed, zwróć Location/status resource i terminal states. Problem Details RFC 9457 może ujednolicić errors z code i traceId; nie ujawniaj stacków i SQL. Rate limit per actor (429) różni się od chwilowej niedostępności backendu (503); retry-after i klient z jitterem ograniczają storm.

2. AuthN, AuthZ, OAuth/OIDC

OAuth 2 to delegowanie dostępu, OIDC dodaje warstwę identity. Access token przeznaczony dla resource server, ID token dla klienta OIDC; nie używaj ID token jako dowolnego API credential. JWT: verify podpis i allowed algorithms, issuer, audience, expiry/not-before oraz uprawnienia, nie decode jako verify. JWKS cache według kid, rotacja kluczy i bounded refresh (unikaj DoS przez losowe kid). Authorization code + PKCE dla publicznych klientów; client credentials dla service identity. Refresh token rotation i reuse detection zależą od providera; access token o krótkim TTL ogranicza okno, nie oznacza natychmiastowego revoke. RBAC plus resource-level ownership, tenant scope w DB, deny by default. Nie polegaj na frontendzie ani API Gateway jako jedynym punkcie kontroli. Cookie auth wymaga CSRF defense; SameSite to warstwa ochrony, nie zawsze wystarczająca.

3. Security boundaries i validation

Waliduj rozmiar i schemat body przed drogą pracą, limity nesting/array/strings, whitelist pól aktualizowanych (mass assignment). SQL values przez parameters, identifiers przez allowlist; ORM raw queries nadal ryzykowne. BOLA: każdy lookup po ID musi kontrolować tenant i permission; RLS może być defense-in-depth, ale pooled connection wymaga transaction-scoped kontekstu. XSS/CSRF/CORS zależą od przeglądarki, SSRF od serwerowego fetch; blokuj nieautoryzowane destinations, redirect, private/link-local addresses i stosuj egress controls. Upload quarantine, typ na podstawie bajtów, ogranicz dekompresję. Logi nie powinny zawierać Authorization, cookies, presigned URLs ani pełnych payloadów z PII. Dependency pinning, scan, SBOM, secret scan oraz rotation. IAM.

4. Idempotent create — transakcja i kontrakt

Przykład w warstwie SQL (uproszczony algorytm, nie gotowa implementacja):
BEGIN;
INSERT INTO request_keys(tenant_id, key, payload_hash)
VALUES ($1,$2,$3)
ON CONFLICT (tenant_id,key) DO NOTHING
RETURNING key;
-- winner: INSERT order, INSERT outbox, UPDATE request_keys result
-- loser: SELECT hash/result w kolejnej instrukcji, porównaj hash
COMMIT;
W READ COMMITTED przegrany czeka na commit zwycięzcy przy konflikcie unique, następny SELECT widzi wynik. Jeśli zwycięzca rollback, druga próba może zostać winner. Hash powinien uwzględniać canonical payload i operation scope; klucz z innym requestem → konflikt. Transakcja nie zawiera wywołania SAP/płatności. Jeśli klucz jest zapisany przed osobną pracą, IN_PROGRESS wymaga lease/recovery i stanu terminalnego. Retencja musi obejmować okres retry klienta. Po utracie odpowiedzi bezpieczny retry wraca do wyniku; po timeout COMMIT outcome jest nieznany. PostgreSQL.

5. REST, gRPC i WebSocket operacyjnie

REST/HTTP: cache-control, conditional requests, stable pagination, request ID; gRPC: deadlines, status codes, protobuf compatibility (nie reuse numerów pól, reserve usunięte), streaming flow control. HTTP/2 multiplexing nie usuwa TCP-level head-of-line i nie gwarantuje automatycznej retry safety. WebSocket: handshake auth, connection lifecycle, heartbeat, reconnect z exponential jitter, sequence/resume token do uzupełnienia brakujących eventów. Po reconnect klient musi odtworzyć subskrypcję i pobrać snapshot/delta. Scale horizontal: sticky sessions nie zastępują wspólnego pub/sub; Node Redis adapter rozsyła eventy, ale Redis Pub/Sub nie jest durable queue. Duplikaty po reconnect i out-of-order obsługuj per entity version. Socket.IO nie jest protokołem identycznym z raw WebSocket. Przy server push rate-limit per user, cleanup i bounded outgoing buffer.

6. Rate limiting i kontrola zasobów

Token bucket dopuszcza burst, fixed window ma skok na granicy, sliding window wygładza kosztem stanu, leaky bucket może wymuszać tempo. Globalny limit w multi-instance wymaga atomowego współdzielonego stanu (np. Redis Lua) lub przybliżonego rozdziału capacity. Per-user i per-route quota plus globalny limit concurrency, osobno dla kosztownych operacji. Nie ustawiaj rate limitu wyłącznie z liczby connections DB; mierz service time i CPU. Fail-open vs fail-closed przy awarii limitera zależy od ryzyka (public abuse vs krytyczna dostępność). Bulkhead na downstream, request deadline, bounded queue. API Gateway · System design.
