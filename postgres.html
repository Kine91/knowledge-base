PostgreSQL w praktyce

Indeksy, transakcje, izolacja, pool, wydajność

EXPLAIN i indeksy

EXPLAIN (ANALYZE, BUFFERS) pokazuje rzeczywisty plan i I/O; uruchamia zapytanie. B-tree nadaje się do equality/range i sortowania z uwzględnieniem kolejności kolumn.

Praktyka / decyzja projektowa

SELECT * FROM orders WHERE customer_id=$1 ORDER BY created_at DESC LIMIT 20; rozważ indeks (customer_id, created_at DESC).

Zagadnienie 2 / 5

Transakcje i izolacja

Domyślny READ COMMITTED daje snapshot na poziomie instrukcji; nie zapobiega wszystkim race conditions. SELECT ... FOR UPDATE blokuje wybrane rekordy; SERIALIZABLE wymaga retry serialization failures.

Praktyka / decyzja projektowa

Rezerwacja stanu: UPDATE inventory SET available=available-$1 WHERE sku=$2 AND available >= $1 RETURNING available; atomowo egzekwuje invariant.

Zagadnienie 3 / 5

Idempotency keys

POST może zostać ponowiony po utracie odpowiedzi. Zapisz klucz, hash requestu, status i wynik w transakcji; UNIQUE(scope,key). Ponowienie tego samego requestu zwraca wcześniejszy rezultat.

Praktyka / decyzja projektowa

Dla tego samego klucza z innym payloadem zwróć 409; zabezpiecz równoległe requesty i przypadek IN_PROGRESS.

Zagadnienie 4 / 5

Pooling i limity

Connection to zasób, nie request. Wiele podów × pool size łatwo przekracza max_connections. Mierz czas zajęcia, queue wait i aktywne sesje.

Praktyka / decyzja projektowa

20 podów × 20 connections = 400; zostaw rezerwę na migracje, monitoring i operacje administracyjne. Przy Lambda rozważ RDS Proxy/PgBouncer.

Zagadnienie 5 / 5

Migracje zero downtime

Stosuj expand → migrate/backfill → contract. Najpierw nowa kolumna nullable, aplikacja obsługuje oba formaty, backfill w batchach, potem constraint i usunięcie starej.

Praktyka / decyzja projektowa

CREATE INDEX CONCURRENTLY minimalizuje blokowanie zapisów, ale ma ograniczenia transakcyjne; planuj lock timeout i rollback.
