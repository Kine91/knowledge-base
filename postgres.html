PostgreSQL — concurrency, storage i performance

MVCC, WAL, izolacja, indeksy, plany, pooling, migracje i odzyskiwanie

1. MVCC, snapshot i VACUUM

UPDATE tworzy nową wersję tuple; stare wersje pozostają dla transakcji, których snapshot je widzi. MVCC pozwala czytać bez blokowania zwykłych zapisów, ale writers nadal rywalizują o row locks. VACUUM odzyskuje przestrzeń do ponownego użycia i zamraża transaction IDs, autovacuum działa per tabela według progów. Długie transakcje/idle in transaction utrzymują stare snapshoty, zwiększają bloat i mogą powstrzymywać vacuum. Replication slot może zatrzymać WAL i wypełnić dysk. VACUUM FULL przepisuje tabelę i blokuje ją; nie jest rutynowym lekarstwem. Monitoruj pg_stat_user_tables (n_dead_tup, last_autovacuum), pg_stat_activity xact_start i pg_replication_slots; progi autovacuum dostosuj do dużych/hot tables. HOT update możliwy gdy indeksowane kolumny się nie zmieniają i strona ma miejsce; fillfactor jest trade-off.

2. WAL, commit i replication

Write-ahead log zapisuje zmiany przed flush stron danych. Przy synchronous_commit=on commit czeka na wymagany flush WAL; konfiguracje replikacji synchronicznej mogą dodawać oczekiwanie na standby. Wyłączenie synchronous_commit może stracić ostatnie potwierdzone transakcje przy awarii, choć baza pozostaje spójna. Checkpoints i full page writes wpływają na I/O i WAL volume. Physical streaming replication kopiuje WAL, logical replication działa na zmianach relacji i wymaga kompatybilności schematu. Replica lag oznacza stale reads. Failover po utracie odpowiedzi COMMIT daje unknown outcome: użyj idempotency key i odczytu stanu, nie bezwarunkowego ponowienia. PITR wymaga backupu bazowego i WAL; testuj restore, RPO/RTO oraz dostępność kluczy.

3. Izolacja i anomalie

READ COMMITTED: snapshot per statement, nonrepeatable read możliwy; UPDATE może czekać na konkurencyjny zapis i ponownie sprawdzić WHERE. REPEATABLE READ w PostgreSQL to snapshot isolation: brak phantom reads w standardowym sensie, ale write skew możliwy (dwóch lekarzy równolegle wyłącza dyżur widząc drugiego aktywnego). SERIALIZABLE używa SSI i wykrywa niebezpieczne zależności, może zwrócić SQLSTATE 40001; ponów całą transakcję, nie tylko ostatni SQL. Deadlock 40P01: baza przerywa jedną transakcję; zachowuj stałą kolejność blokowania i retry z jitter. Nie trzymaj transakcji podczas HTTP call do SAP.

4. Atomowe invariants i locks

Przykład rezerwacji ilości dodatniej:
UPDATE inventory
SET available = available - $1
WHERE sku = $2 AND available >= $1 AND $1 > 0
RETURNING available;
Wynik zero rows oznacza brak rezerwacji; CHECK(available >= 0) jako dodatkowa ochrona. SELECT FOR UPDATE gdy decyzja zależy od kilku pól; dla zakresu wielu rekordów rozważ constraints/serializable, row lock nie blokuje nieistniejącego rekordu. Optimistic locking: UPDATE ... WHERE id=$1 AND version=$2 SET version=version+1 (SET przed WHERE w rzeczywistym SQL); brak row → konflikt. Advisory locks są kooperacyjne, transaction-scoped zwykle bezpieczniejsze przy poolingu. SKIP LOCKED nadaje się do claim zadań, nie do spójnego odczytu biznesowego. lock_timeout i statement_timeout ustaw oddzielnie, idle_in_transaction_session_timeout chroni przed wiszącą transakcją.

5. Indeksy i plany wykonania

B-tree equality/range/order; composite (tenant_id, created_at DESC, id DESC) dobrze wspiera tenant equality i keyset pagination. Partial index WHERE status='PENDING' ogranicza koszt, planner musi móc udowodnić predykat. INCLUDE umożliwia index-only scan, ale heap visibility map decyduje o heap fetches. GIN dla jsonb/array/full-text (droższe zapisy), GiST dla przestrzeni/range, BRIN dla dużych fizycznie skorelowanych tabel. Indeks na expression lower(email) wymaga zgodnego predykatu. EXPLAIN (ANALYZE, BUFFERS) wykonuje zapytanie: na DML użyj bezpiecznego środowiska, nie zakładaj że rollback cofa efekty zewnętrzne. Porównaj estimated vs actual rows (statystyki/selectivity), loops (multiply rows/time per loop), shared hit/read, temp spill, sort method, nested loop vs hash/merge join. Seq scan nie jest błędem dla dużej części tabeli. ANALYZE, extended statistics przy skorelowanych kolumnach; pg_stat_statements dla total time, mean, calls, rows, nie tylko najwolniejszego requestu.

6. Pagination, N+1, batching

OFFSET rośnie kosztowo i może pomijać/duplikować rekordy podczas zmian. Stabilny keyset:
SELECT id, created_at, status FROM orders
WHERE tenant_id=$1 AND (created_at,id) < ($2,$3)
ORDER BY created_at DESC,id DESC LIMIT 50;
Cursor musi zawierać tie-breaker i być walidowany. Współbieżne zmiany sort key mogą nadal przesuwać rekordy; dla eksportów potrzebny snapshot/ustalona granica. N+1 wykryj po query count i traces; użyj join, batch IN/ANY lub DataLoader per request, nie globalnie dla wielu tenantów. Batch insert/COPY redukuje round trips, ale wielka transakcja zwiększa WAL/locks i czas rollback. Dla backfill chunk po PK, checkpoint, idempotency.

7. Pooling i capacity

Postgres tworzy backend process per connection; więcej sesji nie zwiększa liniowo throughput i zużywa RAM (work_mem per sort/hash node, nie per baza). Pool per process; 20 replik × 20 = 400; rolling overlap może podwoić. PgBouncer session pooling zachowuje session state, transaction pooling zwalnia connection po transakcji, nie zakładaj trwałego SET/temp tables/listen/session locks; prepared statements zależą od wersji/konfiguracji. node-postgres: transakcja zawsze na tym samym client, release w finally; pool.query nie gwarantuje tego dla kolejnych instrukcji. Ustaw acquisition timeout i bounded intake. Mierz active/idle/waiting connections, query latency i wait_event_type. RDS Proxy i PgBouncer multiplexują, nie przyspieszają SQL. Lambda i DB.

8. Idempotencja i outbox — konkretna transakcja

UNIQUE(tenant_id,idempotency_key) + hash z kanonicznego payloadu. Dla tej samej operacji zapisz rezultat razem z biznesową zmianą. Równoległa próba INSERT ... ON CONFLICT DO NOTHING może czekać na commit pierwszej; po konflikcie odczytaj istniejący wynik w nowej instrukcji READ COMMITTED. Inny hash → 409. Dla event consumer:
BEGIN;
INSERT INTO inbox(consumer,event_id) VALUES ($1,$2)
ON CONFLICT DO NOTHING RETURNING event_id;
-- jeśli zwrócono wiersz: wykonaj zmianę i ewentualny outbox
COMMIT;
-- dopiero teraz ack wiadomości
Retencja inbox odpowiada maksymalnemu czasowi replay; zewnętrzne side effects wymagają dedup po stronie dostawcy. Messaging.

9. Migracje i diagnostyka produkcyjna

Expand/contract: dodaj kompatybilną kolumnę, deploy kodu, backfill małymi batchami, zweryfikuj constraint, usuń starą po wygaszeniu klientów. CREATE INDEX CONCURRENTLY poza transaction block, po błędzie sprawdź invalid index. DDL może czekać na lock i blokować kolejne zapytania w kolejce, ustaw lock_timeout i retry migracji. ADD constraint NOT VALID + VALIDATE tam gdzie wspierane; testuj na rozmiarze danych produkcji. pg_stat_activity, pg_locks, pg_blocking_pids(pid), wait events odróżniają CPU, lock, I/O i client idle. Najpierw ustal blocker i ryzyko przerwania; pg_cancel_backend przerywa zapytanie, pg_terminate_backend kończy sesję. Nie wykonuj masowo terminate bez zrozumienia skutku. Backup restore, test failover, connection recovery i migracje są częścią Definition of Done.
