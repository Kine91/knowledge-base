AWS Lambda — execution model, scaling i ograniczenia

Techniczne kompendium dla inżyniera budującego produkcyjne systemy w Node.js/TypeScript. Koncentruje się na semantyce wykonania, granicach i kompromisach, bez wprowadzenia do podstaw serverless.

1. Co jest jednostką wykonania?

W standardowej Lambda Event Function AWS zarządza środowiskami wykonawczymi. Jedno środowisko wykonuje pojedynczą inwokację na raz; kolejne wywołanie może użyć tego samego środowiska sekwencyjnie. Gdy wzrasta liczba równoległych wywołań, Lambda tworzy kolejne środowiska. To nie jest jeden proces Node.js obsługujący wszystkie żądania API.

Cykl życia: Init → Invoke (potencjalnie wielokrotnie) → Shutdown. Init obejmuje extensions, runtime bootstrap i inicjalizację modułów. Po zakończeniu Invoke środowisko może zostać zamrożone; AWS może je później wznowić lub zakończyć bez ostrzeżenia. Zakończenie nie jest hookiem, na którym można oprzeć gwarancję zapisania danych.

Init może pojawić się również po awarii/timeout podczas kolejnej inwokacji (suppressed init) i nie zawsze jest bezpośrednio widoczny jako osobny START w zwykłych logach. Telemetry API raportuje fazy Init, w tym phase=invoke.

Wniosek architektoniczny

Nie zakładaj ani świeżego procesu dla każdego żądania, ani trwałości procesu po odpowiedzi. Żadna istotna informacja biznesowa nie może istnieć tylko w pamięci środowiska Lambda.

2. Cold / warm state i semantyka pamięci

Cold start to inicjalizacja nowego środowiska. Warm invocation może użyć już załadowanych modułów, cache, agentów HTTP, socketów i plików w /tmp. Globalne zmienne są współdzielone między kolejnymi wywołaniami tego samego środowiska; nie są jednak współdzielone pomiędzy równoległymi środowiskami.

import { S3Client } from "@aws-sdk/client-s3";
const s3 = new S3Client({}); // init once per environment
let cachedConfig: { value: string; loadedAt: number } | undefined;
export async function handler(event: { tenantId: string }) {
  // Never cache tenant-specific authorization in a process global.
  if (!cachedConfig || Date.now() - cachedConfig.loadedAt > 60_000) {
    cachedConfig = { value: await loadNonSensitiveConfig(), loadedAt: Date.now() };
  }
  return await processTenantRequest(event.tenantId, s3, cachedConfig.value);
}

Przykład ilustruje cache konfiguracji bez danych konkretnego tenanta. W produkcji trzeba dodatkowo obsłużyć błąd pobrania, walidację konfiguracji i ewentualnie pojedynczy in-flight refresh. Warm cache jest optymalizacją, nie źródłem prawdy. AWS SDK klienta warto inicjalizować poza handlerem, natomiast sekret i autoryzację należy kontrolować pod kątem TTL i rotacji.

Po thaw połączenia TCP mogą być martwe. Nawet jeśli klient był zainicjalizowany globalnie, pierwsze żądanie może zakończyć się ECONNRESET; obsłuż odzyskiwalne błędy oraz rozsądne timeouty. Nie zakładaj, że timery uruchomione poza handlerem gwarantowanie dokończą pracę po jego powrocie.

Pułapka bezpieczeństwa

Nigdy nie zapamiętuj w module bieżącego użytkownika, tokenu z żądania, ID transakcji czy autoryzacji tenant-specific. Kolejna inwokacja może należeć do innego użytkownika.

3. Skąd bierze się opóźnienie cold start?

W koszt wejścia wchodzą przygotowanie środowiska, startup runtime, ładowanie zależności, top-level code i extensions. Rozmiar paczki jest tylko jednym z czynników; import kosztownej biblioteki lub inicjalizacja zewnętrznego klienta może dominować. W Node.js zwróć uwagę na duże dependency trees, top-level await, synchronizowane sekrety i inicjalizację ORM.

Analizuj osobno Init Duration, czas samego handlera, p50/p95/p99 i udział cold starts. Redukuj bundle przez tree shaking i selektywne importy, usuń initialization I/O z krytycznej ścieżki, tam gdzie semantyka na to pozwala. Zwiększenie memory zwiększa też dostępną moc CPU, więc może skrócić init i wykonanie; oceń wpływ na całkowity koszt, nie tylko czas.

Reserved concurrency rezerwuje limit współbieżności, ale nie rozgrzewa środowisk. Provisioned concurrency przygotowuje określoną pulę środowisk z wyprzedzeniem i kosztuje dodatkowo; alokacja nie następuje natychmiast. Ruch powyżej puli może przejść na on-demand albo być throttle'owany — zależy od reserved/account limits.

Ważne

«Pingowanie Lambdy co 5 minut» nie daje gwarancji braku cold starts, bo AWS może zastępować środowiska i skalować nowe. Latency SLO wymaga pomiarów i świadomego doboru provisioning.

4. Concurrency ≠ requests per second

Przybliżenie w stanie stabilnym (Little's Law): concurrency ≈ request rate × average duration. Dla 5000 RPS i 200 ms średniego czasu wychodzi około 1000 równoległych inwokacji. To tylko szacunek capacity: dystrybucja opóźnień, bursty i p99 wymagają zapasu.

5,000 req/s × 0.2 s = 1,000 concurrent invocations
5,000 req/s × 0.02 s = 100 concurrent invocations
BUT: RPS quotas and scaling rate can still throttle short requests.

Dla standardowych Event Functions AWS publikuje domyślną regionalną pulę 1000 concurrent executions na konto (quota podlegająca zwiększeniu), osobne ustawienia reserved/provisioned i funkcjonalny limit wzrostu 1000 nowych environments / 10 s na funkcję. Dla synchronicznych invoke dodatkowy limit RPS to 10 × odpowiedni limit concurrency; standardowe środowisko może obsłużyć do 10 requestów/s. Asynchroniczne invoke nie mają tej samej reguły 10 RPS per environment. Provisioned concurrency ma odrębny limit na alias/wersję. Bardzo krótki handler może dojść do RPS quota jeszcze przed saturacją średniej liczby in-flight requestów.

Ustawienie reserved concurrency = 0 to praktyczny bezpiecznik wyłączający kolejne wywołania tej funkcji; dla systemów event-driven trzeba rozumieć konsekwencje opóźnień/retry w source. Quota dotyczy konta i Regionu, a nie automatycznie całego globalnego systemu.

Capacity planning

Przy autoscalingu Lambdy ograniczenie downstream (RDS, SAP API, partner rate limit) jest często ważniejsze niż maksymalna skalowalność samej Lambdy. Celowo ogranicz concurrency workerów, aby nie zalać zależności.

6. RDS, pool połączeń i VPC

Jedno środowisko może utrzymywać własny pool. Gdy Lambda skaluje do setek środowisk, suma połączeń może zabić PostgreSQL nawet wtedy, gdy CPU Lambdy jest daleko od limitu. Najpierw policz environments × connectionsPerEnvironment oraz połączenia innych aplikacji i rezerwę administracyjną.

Reserved concurrency: 200
DB connections per environment: 3
Worst-case Lambda-side demand: ~600 DB connections
DB safe budget for Lambda: 100
=> cap concurrency / use a proxy / reduce DB connection occupancy.

RDS Proxy może redukować churn i multiplexować połączenia do bazy, ale długie transakcje i stan sesji mogą prowadzić do pinning i ograniczać korzyść. RDS Proxy nie tworzy dodatkowej mocy obliczeniowej dla SQL; mierz rzeczywistą liczbę aktywnych sesji, wait times i throughput.

Przy funkcji podłączonej do VPC stosowane są Hyperplane ENI; sprawdź SG, route tables, NAT lub VPC endpoints, DNS i sieciową ścieżkę do RDS. «Lambda w publicznym subnet» nie jest synonimem posiadania publicznego IP. Udostępnienie dostępu do Internetu wymaga właściwej konfiguracji sieci.

Praktyczna polityka

Dla write-intensive event workers projektuj limity concurrency per event source / funkcja, batchowanie oraz retry z jitterem. Dla krótkiego API synchronizowanego z DB zapewnij backpressure i ograniczenie czasów oczekiwania.

7. Sync, async i SQS: trzy różne semantyki porażki

Sync invoke: wywołujący czeka na wynik, a odpowiedzialność za ponowienie jest zwykle po stronie klienta lub integracji. Po timeout klient nie wie automatycznie, czy operacja z efektem ubocznym się udała.

Async invoke: Lambda może przyjąć zdarzenie do swojej wewnętrznej kolejki. AWS domyślnie ponawia błędy funkcji maksymalnie dwa razy; throttling i błędy systemowe mają odrębny mechanizm ponawiania i ograniczenie wieku zdarzenia. Konfiguruj on-failure destination, event age, retry attempts i metryki AsyncEventsDropped/AsyncEventAge.

SQS event source mapping: poller pobiera batch, invokes funkcję i usuwa wiadomości po sukcesie. Gdy batch się nie powiedzie, domyślnie wraca cały batch; ReportBatchItemFailures pozwala zwrócić identyfikatory pojedynczych nieudanych rekordów. SQS to at-least-once — poprawność biznesowa musi opierać się na idempotencji.

import type { SQSEvent, SQSBatchResponse } from "aws-lambda";
export async function handler(event: SQSEvent): Promise<SQSBatchResponse> {
  const batchItemFailures: { itemIdentifier: string }[] = [];
  for (const record of event.Records) {
    try {
      const parsed = parseAndValidateEvent(JSON.parse(record.body));
      await processIdempotently(parsed.eventId, parsed);
    } catch (error) {
      console.error("record_failed", { id: record.messageId });
      batchItemFailures.push({ itemIdentifier: record.messageId });
    }
  }
  return { batchItemFailures };
}

Istotne: taki kod wymaga włączenia ReportBatchItemFailures w event source mapping. Idempotencja oparta wyłącznie na messageId może nie wystarczyć, gdy producer wyśle logicznie ten sam event ponownie jako nową wiadomość. Stosuj stabilny event/business ID i unikalny constraint w trwałym magazynie.

Przy FIFO batchach zachowaj semantykę kolejności: po pierwszym błędzie zatrzymaj batch i zgłoś wszystkie rekordy nieudane oraz nieprzetworzone. Visibility timeout dobieraj do timeoutu funkcji oraz batch window; AWS zaleca co najmniej 6 × timeout Lambdy plus skonfigurowany batching window dla SQS trigger.

8. Operacje produkcyjne i świadome kompromisy

  • Latencja: p50/p95/p99, init duration, provisioned concurrency spillover i cold-start ratio. Nie optymalizuj średniej, jeśli SLO zależy od ogona.
  • Capacity: ConcurrentExecutions, UnreservedConcurrentExecutions, Throttles, queue age, RDS sessions, SAP quota. Łącz metryki platformy i biznesowe.
  • Timeout budget: upstream HTTP timeout < Lambda timeout? Jeśli tak, może powstać „orphaned work”; ustaw jawne budżety i idempotencję.
  • Rotacja sekretów: globalny cache wymaga TTL/invalidation; nie polegaj na restarcie środowiska.
  • Deployment: versions + aliases, canary, alarm rollback, kompatybilne migracje DB; provisioned concurrency przypinaj do wersji/aliasu i uwzględnij czas provisioningu.
  • Spójność: wymuszenie at-least-once na wejściu i idempotencja na wyjściu; outbox chroni przed dual-write między DB i publikacją.
  • Koszt: porównuj GB-s, liczbę invoke, provisioned concurrency, transfer/NAT, CloudWatch logs, RDS proxy i koszt operacyjny.
Kiedy nie wybierać Lambdy?

Długotrwały stabilny serwis z intensywnym connection poolingiem, mocnym affinity do pamięci procesu lub wymaganiami systemowymi może być łatwiejszy i tańszy na Fargate/EC2. Porównaj całościowe SLO i koszt, nie tylko brak zarządzania serwerem.
