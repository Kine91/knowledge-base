S3 — storage, consistency i bezpieczeństwo

Projektowanie uploadów, lifecycle, eventów i dostępu do obiektów

1. Consistency i współbieżność2. Multipart, checksums i direct upload3. Authorization, KMS i public access4. Events i stan dokumentu5. Wydajność, koszty i lifecyclePraktykaLimity i konfiguracja

1. Consistency i współbieżność

S3 zapewnia strong read-after-write dla PUT/DELETE i LIST obiektów, ale nie transakcję wieloobiektową. Nadpisanie klucza jest atomowe dla pojedynczego obiektu; concurrent writers mogą nadpisać sobie dane. If-None-Match: * pozwala warunkowo utworzyć obiekt; If-Match z ETag pozwala chronić aktualizację przy wspieranej operacji. ETag traktuj jako opaque validator, nie zawsze MD5 (multipart, szyfrowanie). Versioning chroni przed nadpisaniem i delete markerem, ale nie zastępuje backup/replication; usunięcie konkretnej wersji może być trwałe. Cross-region replication jest asynchroniczna. Nie uzależniaj poprawności od listowania bucketu jako kolejki.

2. Multipart, checksums i direct upload

Dla dużych plików backend autoryzuje intencję uploadu, tworzy uploadId, wydaje krótkotrwałe presigned URLs dla part numbers, klient wysyła części równolegle i retry tylko failed parts, backend lub klient kończy CompleteMultipartUpload z listą części. Dopiero complete tworzy obiekt. Typowo do 10 000 części; min 5 MiB z wyjątkiem ostatniej, max 5 GiB na część, aktualny limit general-purpose S3 wynosi około 50 TB (dokładnie 50 000 GiB); inne warianty bucketów sprawdzaj osobno. Niezakończone uploady generują koszt, ustaw AbortIncompleteMultipartUpload lifecycle. Sprawdź checksum, rozmiar, ownership i status przed oznaczeniem dokumentu READY. Presigned PUT nie ma takich samych warunków content-length-range jak presigned POST. URL jest bearer capability i wygasa nie później niż credentials podpisującego; nie loguj go.

3. Authorization, KMS i public access

Block Public Access na koncie/buckecie, bucket owner enforced (ACL disabled) gdzie możliwe, role least privilege rozdzielające upload/read/delete. IAM s3:ListBucket dotyczy ARN bucketu, s3:GetObject ARN bucket/key. Prefix nie jest granicą bezpieczeństwa sam w sobie; policy musi ograniczać key/tenant. SSE-S3 lub SSE-KMS, KMS key policy i IAM muszą zezwalać na wymagane operacje; rotacja i cross-account access mają osobne zasady. Bucket keys mogą zmniejszyć liczbę KMS calls. Wymuś TLS przez aws:SecureTransport; CloudFront OAC zamiast publicznego bucketa. CORS nie jest autoryzacją.

4. Events i stan dokumentu

S3 notifications mogą być powtórzone i dostarczone w innej kolejności. Sequencer pozwala porównać kolejność zdarzeń tego samego key (wyrównaj długości hex), nie między kluczami. Worker deduplikuje versionId/event identity, przetwarza konkretną wersję, sprawdza state machine PENDING_UPLOAD → QUARANTINED → SCANNING → READY/REJECTED. Upload oznacza przyjęcie bajtów, nie zaufaną treść. Skanuj rzeczywisty format, malware, zip bombs; oddziel strefę quarantine od publicznie serwowanej. Nie zapisuj rezultatów do tego samego event prefix bez filtra (rekurencyjne wywołania).

5. Wydajność, koszty i lifecycle

S3 skaluje throughput per prefix; AWS podaje orientacyjne poziomy request rates, a przy gwałtownym wzroście możliwe 503 Slow Down. Rozkładaj ruch, retry z jitterem, równoległe range GET i multipart. Cache w CloudFront wymaga wersjonowania nazw i prawidłowego cache key; invalidation nie jest transakcją. Storage class dobieraj do access pattern, minimal storage duration, retrieval fees i czasu odzyskania; lifecycle transitions mają koszt. Object Lock governance/compliance wymaga świadomej polityki retencji; replication nie naprawi uszkodzeń logicznych, jeżeli replikuje je też. Mierz request costs, transfer, bytes, 4xx/5xx, incomplete multipart storage.

Praktyka: upload 2 GiB

Podziel plik na 32 części po 64 MiB, klient wysyła np. 4 równolegle, utrzymuje part number + ETag. Backend generuje immutable key i uploadId, zapisuje PENDING_UPLOAD z expectedSize, expiry i checksum. Po complete sprawdź HeadObject i wynik skanowania. Przy utracie odpowiedzi complete sprawdź status, nie twórz automatycznie drugiego dokumentu. Lifecycle usuwa abandoned multipart, aplikacja usuwa porzucone intencje.

Presigned URL może być używany wielokrotnie do wygaśnięcia; weryfikuj rozmiar i ownership po complete. Jeśli obiekt można nadpisać, skanowana i serwowana wersja mogą się różnić — użyj versionId albo immutable key. Download URL podpisuj po resource authorization.

Granice i performance general-purpose buckets

Dokumentacja AWS (27.11.2026) wskazuje co najmniej 3500 operacji zapisu/usunięcia i 11 000 GET/HEAD na sekundę na partitioned prefix; usługa skaluje się do większych szybkości, lecz nie natychmiast. To nie globalny hard limit bucketu. Obserwuj 503 Slow Down i KMS throttling, w razie potrzeby rozłóż ruch na prefixy i użyj jitter. Dla odczytu dużego obiektu stosuj równoległe range GET, kontroluj liczbę socketów i nie pobieraj całości do pamięci. Optymalizuj względem throughput, time-to-first-byte i kosztu żądań.

Multipart: liczba części × rozmiar określa max object size. Zbyt małe części zwiększą liczbę API requests i ryzyko przekroczenia 10 000 parts, za duże utrudnią retry. Dla 1 TiB potrzebujesz co najmniej ok. 105 MiB na część, więc 128 MiB to rozsądny punkt startu. Upload i download licz w bajtach, nie w długości stringa. Versioning oraz lifecycle noncurrent versions wymagają oddzielnej polityki, aby nie płacić bezterminowo za nadpisane obiekty. Monitoruj koszty retrieval i minimalny czas składowania przy przejściu do klas archiwalnych.
