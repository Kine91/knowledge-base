Strategia testowania Senior

Unit, integration, contract, e2e i testy odporności

1. Piramida i ryzyko2. Failure injection3. Kontrakty i integracje4. Load testing i SLO
Zagadnienie 1 / 4

Piramida i ryzyko

Testy jednostkowe sprawdzają reguły domenowe; integration sprawdzają rzeczywiste DB/queue; contract sprawdzają API; nieliczne e2e krytyczne ścieżki.

Praktyka / decyzja projektowa

Postgres w Testcontainers: test concurrent reservation, rollback, unique constraints; fake repository nie zastąpi tych testów.

Pytanie senior / pułapka

Cel: confidence i szybki feedback, nie 100% coverage jako wskaźnik jakości.

Zagadnienie 2 / 4

Failure injection

Testuj timeout po wykonaniu side-effect, duplikaty SQS, out-of-order messages, utratę połączenia, shutdown i retry exhausted.

Praktyka / decyzja projektowa

Scenariusz: worker zapisuje DB, pada przed DeleteMessage; drugi worker przetwarza to samo eventId, stan nie zmienia się ponownie.

Pytanie senior / pułapka

Bez testów race conditions happy path daje złudne bezpieczeństwo.

Zagadnienie 3 / 4

Kontrakty i integracje

Pact/consumer-driven contracts mogą wcześnie wykryć breaking changes; wersjonuj schemat eventów, dodawaj pola opcjonalnie.

Praktyka / decyzja projektowa

SAP sandbox często jest ograniczony: korzystaj ze stabilnych fixtures i testów mapowania, plus wybrane smoke tests na środowisku integracyjnym.

Pytanie senior / pułapka

Nie zastępuj integracyjnych testów rzeczywistego SQL mockami ORM.

Zagadnienie 4 / 4

Load testing i SLO

k6/Artillery: zdefiniuj traffic mix, ramp-up, spike, soak i kryteria akceptacji p95, errors oraz DB saturation.

Praktyka / decyzja projektowa

Test 5000 req/s: osobno mierzyć API acceptance i końcowy czas przetwarzania kolejki. Obserwuj oldest message age, DB locks, CPU, memory.

Pytanie senior / pułapka

Nie deklaruj, że system «obsługuje 5000 RPS» jeśli kolejka rośnie stale.
