Testowanie — strategia jakości i failure modes

Unit, integration, contract, E2E, concurrency, load, chaos i CI

1. Strategia oparta na ryzyku

Unit tests chronią czyste reguły domenowe; integration testuje adaptery z rzeczywistą DB/brokerem, contract weryfikuje zgodność niezależnych deployów, E2E sprawdza krytyczny przepływ. Nie narzucaj procentowego podziału; koszt i ryzyko decydują. Coverage statement/branch ujawnia nieuruchomione ścieżki, nie correctness; mutation testing wykrywa słabe asercje (np. zmiana > na >= nie powoduje fail). Testuj observable outcome, nie prywatną strukturę metod. Fake clock, seeded random, dependency injection i deterministic IDs ułatwiają kontrolę. Nie mockuj całego use case tylko po to by sprawdzić że mock został wywołany.

2. Integration: PostgreSQL, queues i isolation

Testcontainers z prawdziwą wersją DB, migracje od zera i upgrade, separate schema/database per worker lub reset fixture. Rollback testu działa tylko jeśli kod używa tej samej transakcji; background worker może mieć osobne connection. Test real constraint/lock/SQL i race z dwoma niezależnymi clients; SQLite nie zastępuje PG semantics. Emulator AWS przyspiesza testy, ale nie potwierdza IAM, VPC, service quotas, event source mapping czy exact retry behavior. Wykonuj wybrane testy na izolowanym koncie AWS; tag/TTL cleanup i budżet. Dla async testu czekaj na warunek z deadline, nie fixed sleep. Idempotency test: to samo eventId dwukrotnie, nawet równolegle, jeden trwały efekt.

3. Kontrakty i ewolucja

Consumer-driven contract (np. Pact) opisuje interakcje potrzebne konsumentowi; provider verification uruchamiaj w CI i publikuj wersję. OpenAPI schema diff wykrywa structural breaking changes, ale nie semantyczne np. zmiana waluty. JSON Schema event envelope i test tolerant reader: nowe optional fields, brak starych optional fields, nieznane enum; nie ignoruj required invariants. Weryfikuj zarówno stary consumer + nowy producer, jak i nowy consumer + stary producer w rolling deployment. Dla SAP fixtures uzgodnione z providerem, realny sandbox na najważniejsze operacje.

4. Failure injection i concurrency

Scenariusze: crash po COMMIT przed ack, timeout po side effect, partial batch failure, duplicate/out-of-order event, expired visibility, DB failover, 429 downstream, credential rotation, shutdown w trakcie joba. Dla każdego zdefiniuj invariant: brak podwójnego księgowania, inventory nieujemne, trwały accepted job nie znika, status osiąga terminal/review. Deterministyczna bariera w testach race: dwa requesty odczytują stan, następnie zwolnij oba do write; nie licz na przypadkowy timing. Weryfikuj pełny efekt w DB i liczbę zewnętrznych działań. Chaos w środowisku testowym/izolowanym, z guardrails, stop condition i planem odzyskania; nie wprowadzaj awarii w produkcji bez zgody.

5. Load testing i capacity

Closed model (stała liczba VU) może zmniejszać offered load gdy system zwalnia, ukrywając overload/coordinated omission; open arrival rate testuje wymagany RPS. Definiuj traffic mix, realistic data cardinality, ramp, steady, spike i soak. Mierz accepted RPS vs completed throughput, p50/p95/p99, errors/timeout, event loop delay, pool wait, DB locks, CPU/IO, queue age. Przykład kryteriów (do ustalenia): 5000 RPS przez 10 min, p95 poniżej 250 ms, error rate poniżej 0.1%, queue lag nie rośnie stale; dla async osobno completion SLO. Generator musi mieć capacity; unikaj jednego klienta jako bottleneck. Test cold vs warm, rolling deployment i recovery po burst. Benchmark na realistycznych indeksach/rozmiarze danych, nie pustej DB.

6. Frontend, accessibility i test isolation

React Testing Library sprawdza zachowanie przez role/label, user-event modeluje interakcje; nie assertuj liczby renderów jako głównego kontraktu. MSW symuluje HTTP na granicy sieci, testuj loading/empty/error/retry, stale response, optimistic rollback i auth refresh. Playwright/Cypress: krytyczne ścieżki z izolowanymi kontami i seed data; locators semantyczne i auto-wait, bez arbitrary sleep. Test a11y axe + manual keyboard/focus/screen reader; automatyczne narzędzie nie wykryje wszystkich problemów. Visual regression dla stabilnych komponentów z deterministycznymi fontami/viewport, osobno responsive layout. Nie polegaj wyłącznie na snapshots.

7. CI/CD, flaky tests i release quality

Pipeline: lint/typecheck/unit → integration/contract → build immutable artifact → scan → deploy staging/smoke → canary/production. Parallelize po niezależnych shardach, cache lockfile dependencies, nie cache'uj wyników z niejawnie zmiennym środowiskiem. Flaky test to defekt: zachowaj seed, trace, logs, network; retry w CI może być diagnostyką, nie maskowaniem. Quarantine z właścicielem i deadline; krytyczna ścieżka musi mieć stabilny gate. Migracje testuj backward compatible; po canary oceniaj error budget i business KPI, automatyczny rollback jeśli bezpieczny. Test backup restore i RTO/RPO jest częścią strategii, nie sam unit test. Praktyka: test współbieżności i recovery

Fragment testu integracyjnego Vitest/Jest; helpery wykonują realny SQL na osobnych połączeniach.

it("rezerwuje ostatnią sztukę tylko raz", async () => {
  await seedInventory("SKU", 1);
  const results = await Promise.allSettled([
    reserveWithSeparateClient("SKU", 1),
    reserveWithSeparateClient("SKU", 1)
  ]);
  expect(results.filter(x => x.status === "fulfilled"))
    .toHaveLength(1);
  expect(await available("SKU")).toBe(0);
});

Założenie: reserveWithSeparateClient rzuca domain conflict, jeśli UPDATE zwróci zero wierszy. Dodaj kontrolowaną barierę, gdy chcesz odtworzyć konkretny race read-check-write. Test outbox: commit order+event, crash publishera po send, ponownie publish, przetwórz oba eventy i sprawdź jeden business effect. Używaj migracji produkcyjnych i osobnych połączeń. Przykład to fragment, nie kompletny projekt testowy.
